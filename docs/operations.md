# ling 排错手册

适用版本：0.2.0 预发布；保留的 0.1.3 说明用于区分升级前后的行为。0.3.0 运维验收使用公开 0.2.0 制品，已执行范围见下文，不能据此推导跨版本升级或目标物理环境通过。示例使用本机默认地址；实际排查须指定与应用相同的实例、数据库、认证和 TLS 设置。先记录两个程序的版本，再决定是否需要改配置或停机。

```sh
ling --version
ling-cli --version
ling-cli -c 'PING'
ling-cli -c 'INFO events'
```

`PING` 成功只证明这条连接可用。`INFO events` 的 `committed`、`dropped`、`redelivered` 是实例统计，不等于某组已收到或确认；`consumer_groups` 才有各组的 `pending` 和分片 `watermarks`。在故障前后各取一次，比只看单个数值更有用。共享日志时去除密码、令牌、私钥、业务 Key/Value。

## 消费者没有收到事件，或收到重复事件

| 观测 | 怎么区分 | 下一步 |
|---|---|---|
| 建组成功，首条迟迟不到 | 核对 SELECT 的库、pattern、建组时点。新组从当时流尾开始，不补发建组前的事件。已有匹配提交且组的 `pending=0` 时，不能据此认定没有事件：小 `events.buffer_bytes` 可能容得下空组，却容不下第一笔交付记账（R-14） | 在隔离实例先建组，再产生一个已知匹配的事件；对照同组窗口和较宽预算，不要重建生产组。修改事件预算须按[配置](config.md)安排重启；Fast 组不跨进程，缓存重启后为空。 |
| 已有 pending，但新交付停滞 | 同组所有消费者共享窗口；后序 ACK 可被早先的空洞挡住。Fast 的 `dropped` 增长与 Reliable 的磁盘容量不足是两件事 | 查最早未确认的业务处理是否完成，只对确实处理完成且交付给该组的 ID 做 ACK。不要跳水位或确认猜出的 ID。 |
| CLI 已打印事件、退出却又收到同一 ID | 打印不是 ACK。0.1.3 显式 ACK 模式下 stdin EOF 可能以成功状态结束且未确认（C-10）；ACK 成功前断线也可重投 | 保留可读 stdin 并显式确认；下游按完整 event_id 幂等处理。`--auto-ack` 在输出刷新后即确认，只适用于把「成功输出」视为处理完成的场景。 |
| 订阅结果与 SCAN MATCH 不同 | 0.1.4 已统一 KEYS、SCAN MATCH 与订阅的通配实现；0.1.3 的重叠星号模式可能产生不一致（R-10） | 先核对服务端版本、数据库、同字面 pattern 与同一个 Key，再在隔离库比较；订阅过滤不能代替访问控制。 |
| `ERR_OFFSET_EXPIRED` / `ERR_STREAM_MISMATCH` | 前者表示需要的历史不再可用；后者表示流身份变了。二者都不是「没消息」 | 停止自动重连循环，核对实例、旧 stream_id、组及业务检查点。由业务明确决定补偿或从新位置开始；不要自动换组名、跳到流尾或删除 Journal。 |

## 写入超时、日志满或恢复失败

- **发送后断线/超时，或 `ERR_COMMIT_UNKNOWN`：** 结果未知。保存时间、命令类别、数据库和业务侧去重标识；重新建连，只读核对业务状态或已知事件。一次 GET 的当前值不能证明那次 INCR、弹出操作或 Batch 的每一项都执行过或没执行。没有足够证据就保留未知状态，不整批重放。协议的 Request ID 不是幂等键。
- **`ERR_JOURNAL_FULL`：** 这是逻辑容量拒绝，按下文区分 Journal 配额、实际磁盘空间与消费窗口。清理受保留期约束；ACK 并不保证立即释放文件空间。不要为恢复写入而删日志文件或切换到 Fast。
- **`ERR_JOURNAL_UNAVAILABLE` 或启动报告损坏：** 先确认平台、实际目录、服务用户、磁盘状态与独占使用情况。怀疑记录损坏时停止新的读写/自动重启，停服后保留整个目录的副本、错误位置和版本。0.1.4 起运行期遍历只读，启动仅修复有充分证据的未提交尾部；0.1.3 曾共用可修尾遍历路径（R-09）。按下文在副本上核对，既不能保证挽回所有事件，也不能用 Journal 恢复缓存。

## 容量规划与观测

先分别记录 `INFO memory`、`INFO keyspace`、`INFO events` 和 `CONFIG GET` 的有效配置，并对照操作系统的进程 RSS、文件系统已用/可用字节。`engine.max_memory_bytes` 只约束缓存索引、Key、Value、条目元数据和到期索引预留；网络缓冲、事件缓冲、程序本身、分配器碎片与 Journal 页缓存另计。受管预算不是进程或整机的内存上限。

在隔离实例使用实际 Key 长度、Value 类型与大小分布，分档增加活跃 Key，分别采集预热后、稳定负载及删除后的受管字节与 RSS。以新增受管字节除以新增活跃 Key 估算该负载的计费，混合类型分别测量；不要直接以 Value 字节数估算容量。`FLUSHDB ASYNC` 的退役索引释放前仍计费，受管归零后 RSS 也可能保留。需要的部署余量由同配置的并发连接、事件消费和稳定负载实测决定，本手册不提供未经测量的通用百分比。

以下是 0.1.5 候选的历史测量，均为 128 MiB 受管预算、每库 4 Shard、事件关闭、4 个闭环连接；环境与限制见[基线重测](testing.md#015-可观测性与基线重测)。它们说明如何核算，不是 0.2.0 或目标机器的容量承诺。

| Bytes Value / 活跃 Key | 预填充受管字节 | 每 Key 计费 | 负载结束 RSS / 清库后 RSS | 原始记录 |
|---|---:|---:|---:|---|
| 64 B / 1,000 | 3,970,000 | 3,970 B | 7,757,824 / 7,774,208 B | [get-1](../benchmarks/results/v015-2026-11-17/candidate-full-44067271629/get-1/result.json) |
| 4 KiB / 1,000 | 8,002,000 | 8,002 B | 15,056,896 / 13,369,344 B | [medium-1](../benchmarks/results/v015-2026-11-17/candidate-full-44067271629/medium-1/result.json) |
| 64 KiB / 256 | 17,777,152 | 69,442 B | 36,802,560 / 31,432,704 B | [large-1](../benchmarks/results/v015-2026-11-17/candidate-full-44067271629/large-1/result.json) |

三例清库后受管字节都为零，RSS 未归零。0.3.0 目标环境的完整容量曲线和多日资源趋势仍待验收；不要将历史短样本当作新的校准结果。

Reliable 的磁盘规划另做一份预算：在具有代表性 Key、写入率、组数量和 ACK 频率的负载下，记录完整 Journal 事务、消费元数据和保留窗口内的增长；一次净文件增长可能包含压缩，不能直接当作事件产生速率。按需要保留的完整活动文件估算容量，`event_journal.max_bytes` 至少要容纳其两倍，因为活动文件至多占总预算一半，另一半预留原子替换；此外还有控制记录预留，不能把半个总预算全部按事件 Payload 分配。组快照总量和拓扑检查点各受 `max_bytes / 16` 约束，具体关系见[磁盘格式](persistence.md#磁盘格式-v1)。这些只是必要约束，最终值仍须通过完整负载验收。

实际磁盘还要容纳同卷的其他实例、已停用策略目录、备份、日志和证据，不能仅相加活动实例的 `journal_bytes`。WSL 同时核对 guest 文件系统和承载 VHDX 的宿主卷；本轮验收在两侧任一可用空间低于 10 GiB 时停止，这只是测试保护阈值，不是生产容量建议。

## 停服归档与同版本恢复演练

这是人工停服归档和隔离副本的核对流程，不是在线备份、缓存恢复或跨主机自动接管能力。先将应用切入维护状态，暂停新请求与消费者，并停止服务管理器的自动重启；按[安装方式](install.md)停止正确实例，确认进程结束、端口释放。`SHUTDOWN` 返回成功后也要等待进程退出。

1. 保存准确服务端和 CLI 版本、二进制 SHA-256、配置及其 SHA-256、实际数据库数和解析后的 Shard 数、服务用户及目录权限。保存客户端 HELLO 的 `stream_id`、已成功提交的事件 ID、每组已确认 ACK 和未确认空洞；`INFO events` 的汇总计数不能替代这些证据。
2. 在所有写入者退出后复制整个 `event_journal.dir`，包含 `LOCK`、`journal.lgj` 及存在时的 `journal.next`。记录每个文件的相对路径、字节数、SHA-256、所有者和权限；复制完成后逐文件核对。普通内容复制不等于保留 uid/gid，恢复前应单独核对目标服务用户的读写权限。保留原件，只分析新副本。
3. 使用同一已核验二进制、同数据库数和明确固定的实际 Shard 数，在独立目录与回环端口启动副本。不要让两个进程共用一个 Journal，也不要因启动失败改用空目录；新目录意味着新 `stream_id`。自动 Shard 数可能随机器改变，不能以配置文件同为 `0` 推断拓扑一致。
4. 确认恢复完成后再接入测试客户端。各数据库 `DBSIZE` 应为零；核对 `stream_id` 与保留范围内已确认提交的完整事件、命名组 ACK/空洞是否相符。只有已交付且业务处理完成的事件才能 ACK；不得为核对而确认未知 ID。在演练副本上产生一条新的测试事件，核对其所在 `(db, shard)` 的序号从原流尾继续；不能把不同分片序号合并为全局顺序。
5. 正常停止演练副本，归档恢复后的完整目录和日志，比较原件与副本变化；启动修尾和正常写入只能发生在副本。只有全部核对满足业务恢复要求后再安排接流，旧原件继续保留。本轮只演练了隔离副本，未执行生产切换。

2026-11-18 的同版本演练已核对两库/每库两 Shard：缓存均为空，原 stream_id 保留，第二条事件先 ACK 形成的空洞恢复为重投 1/3/4，已 ACK 的 2 不重投，后继事件序号为 5。同目录第二进程被拒绝，错误 Shard 数也被拒绝且原件不变。复制目录和全部归档逐文件核验已执行；这不是跨版本升级、回退或跨主机迁移验收。详见[存储故障实测](testing.md#030-wsl-存储故障2026-11-18)与[原始证据清单](../benchmarks/results/v030-storage-2026-11-18/manifest.json)。

## 配额、磁盘和损坏处置

| 现象 | 操作顺序 | 已执行的边界 |
|---|---|---|
| `ERR_JOURNAL_FULL` | 保存 `INFO events`、有效 `max_bytes`、保留期、组窗口及实际磁盘余量。确认是提交前拒绝后暂停重试；正常处理已有消费与 ACK，等待按保留契约清理。若需扩大预算，停服归档，在隔离副本修改静态配置并重启核对，再安排正式变更。不能用 `CONFIG SET` 热改预算 | 1 MiB 配额在第 366 次 SET 拒绝，GET 保留 365；ACK 成功，pending=4、journal_bytes=393,190、journal_errors=0。副本扩大到 2 MiB 后恢复同 stream 并成功新写；没有清除历史或缩短保留期 |
| `ERR_COMMIT_UNKNOWN` 后出现 `ERR_JOURNAL_UNAVAILABLE` | 保留未知请求，停止新写入和盲目重连；先保存客户端结果与能取得的 INFO，再按上节停服归档。核查实际空间、权限和 I/O 错误，消除外部原因后只在副本试恢复。完整已提交事务可能恢复；无法判断的尾部也可能明确拒绝 | 64 MiB ext4 镜像内确实发生 `write=-1 ENOSPC`。第 65 次 SET 结果未知，后续 SET 被拒绝，GET 仍为 64；副本因模糊尾拒绝恢复。未测试强制 fsync EIO |
| 订阅先报全局 Journal 故障，随后 ACK 断线 | 保存先到的错误与 ACK 传输结果，保留最后确认的业务位置；断线或 EOF 不能改记为 ACK 成功，也不能推断 ACK 一定未执行 | 本轮先收到明确 `ERR_JOURNAL_UNAVAILABLE`，随后 ACK 得到 EOF，记录为未确认；没有稳定 ACK 错误响应 |
| 目录可读但服务用户不能写 | 用实际服务身份核对目录及文件权限、配置路径和独占进程；不要以 root 能写代替服务用户验证。在副本修复权限后重启，核对流身份与恢复边界 | 同 uid 先正常启动，再将 Journal 设为 0400；真实写权限探针和启动均被拒绝，字节不变。恢复 0600 后同 uid 可启动 |
| 启动发现截断或损坏 | 立即保留 stderr、退出码和完整原件，只在新副本复核。由服务判断可确认短尾，不手工截断、跳记录或编辑 CRC | 完整 1,330 B Journal 后追加 2 B 短头，或追加完整记录但缺末尾 4 B，均恢复到原完整前缀；载荷截断及中段 CRC 错误均拒绝且字节不变 |
| 运行中发现损坏 | 停止新业务请求，归档原件并记录首次错误位置和各订阅结果；恢复流程仍只在副本执行 | 运行中短头与 CRC 损坏均触发全局故障，活跃和空闲订阅获错，后续写入被拒绝，源 Journal 不变 |

本轮发现的 P2 诊断缺陷仍未修复：公开 0.2.0 服务端的启动入口把底层错误转换为通用帮助，载荷截断和 CRC 损坏虽以 `ERR_JOURNAL_UNAVAILABLE`、退出码 1 拒绝启动并保留原件，却丢失契约要求的记录偏移 1240 / 151。不要因 stderr 未给偏移认定 Journal 完好；也不要自行猜测位置修改文件。运行期两项首次错误仍分别报告偏移 783 / 248。存储套件因此整体退出 1，不能记作全部通过；具体失败与限制见[存储故障实测](testing.md#030-wsl-存储故障2026-11-18)。

## 升级与回退前检查

升级前先完成上述停服归档，固定当前与目标两个程序的版本、摘要和来源证明，并阅读两版的格式、配置与平台限制。程序安装和更新器中断恢复按[安装指南](install.md#命令行更新)执行；`ling update --version` 不提供降级，不能把同版本副本恢复当成回退方案。

先用目标版本在隔离副本验证恢复及消费者行为；若计划回退，还需用旧版本和单独副本预先验证其能否读取新版本留下的状态。两个方向任一未验收，都应记录为未验证，不在唯一生产目录上试错。格式或拓扑不兼容时保留旧目录并另行设计切换，不能静默改标签或新建空目录冒充旧流；从较早归档恢复也不能掩盖归档之后的已确认提交和 ACK。

本轮未执行跨版本 Journal 升级/回退、跨主机迁移、在线目录复制、目标生产接流、物理断电或设备写缓存验收。上述升级与回退步骤是待执行的运维要求，相关工作包不能仅凭本文补齐而标为全部完成。

## TTL 看似没变，修订号却在增加

在同一数据库对照 `PEXPIRETIME key`（Unix 毫秒）和 `PTTL key`（剩余毫秒；-1 无期限、-2 不存在）。不要用两次网络查询之间的自然耗时代替单调时钟证据。0.1.4 对相同未来绝对期限、单调期限差严格小于 1 ms 的重设保留原期限及 revision；更大的变化仍按真实修改处理。该容差也可能吸收小于 1 ms 的真实时钟校正。0.1.3 的重复绝对期限曾产生额外 revision（R-13），排查时不要只凭 revision 推断业务值被改写。见[TTL](ttl.md)。

## 启动或升级后服务不可用

| 场景 | 先查什么 | 如何处置 |
|---|---|---|
| Linux 的 Reliable 前台可用，装成服务后起不来 | `systemctl status ling`、`journalctl -u ling -n 100 --no-pager`、`systemctl cat ling`；Journal 相对路径是相对于**配置文件目录**，不是 WorkingDirectory。随包单元只放行 `/var/lib/ling` | 使用[随包示例](../packaging/linux/ling.toml)里的绝对路径 `/var/lib/ling/journal` 并确认服务用户可写；不要放宽整个系统沙箱。若已有历史目录，不要直接指向一个空目录冒充恢复。 |
| Windows 启用 Reliable 得到 `ERR_CONFIG_INVALID` | 0.1.3 在监听前明确拒绝此组合，不是创建目录或改 ACL 就能修好 | 需要持久事件时选择满足同步要求的 Linux/macOS 环境；只有业务能接受不持久化时才显式选 Fast。 |
| 更新没有稳定候选，或者 Windows 助手返回后版本没变 | `ling update --stable --check` 只找正式版；只有预发布时无候选并不表示下载失败。Windows 看输出路径下的 `result.json`：`scheduled` 不等于 `success` | 需要预览版时显式用 `ling update --check` 比较；`unknown` 或中断时先保留结果文件、备份和安装日志，比对 `ling --version`、`ling-cli --version`。版本不一致时暂停使用，按[安装指南](install.md)恢复同一套程序并保留配置/状态，不要盲目重复更新。 |

对照依据：[命令与错误码](commands.md)、[事件与保留](events.md)、[客户端与结果未知](sdk.md)。版本工作包及证据编号见[基线审查](version/baseline-0.1.3.md)。

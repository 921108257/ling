# 设计决策与待验证项

> 状态：v0.3 设计草案。本文记录对 v0.2 首次规划的解释与修订，便于审阅范围变化；不表示实现或基准已经完成。

## 保留的产品方向

独立部署、Rust、自定义协议、Remote-first、内存优先、固定 Shard、多数据库、10 种正交 Value、毫秒 TTL、Key 事件、CLI 优先、Rust / Java / Go SDK 均保留。Redis 兼容、Embedded、集群、跨节点事务、脚本和动态 Shard 仍不在首版范围。

## 对原始规划的修订

| 编号 | v0.2 中的问题或承诺 | v0.3 决策与原因 |
|---|---|---|
| D01 | CLI 定义语义，其他 SDK 是“原生 SDK 的封装” | 规范定义共同语义；CLI 复用 Rust，Java / Go 原生实现协议。避免偶然行为与未声明的 FFI 依赖 |
| D02 | MGET 既是 String 专用又支持所有 Value | GET / GETSET / MGET / MSET 都是通用命令；MGET 逐项返回结果 |
| D03 | Null 映射为 Option::None / nil | 显式 Value::Null，缺失是独立错误；不混淆存在与空值 |
| D04 | 数值、集合相等和深度含糊 | 类型敏感相等、Float 零归一化、NaN 禁止、Set 仅标量；所有容器计深度 |
| D05 | EXAT 标成毫秒，与 EXPIREAT 不同 | EX/EXAT 使用秒，PX/PXAT 使用毫秒；无 TTL 的 SET 清除旧 TTL |
| D06 | 容器/数字缺失时是否创建未定 | 仅 SET / MSET 等显式创建；类型专用命令缺失报错，空容器保留 |
| D07 | db 为 u8，但数据库数可配置且无上限 | 数据库编号统一 u16，数量 1..65536；默认仍为 16，不为每库建立专属线程池 |
| D08 | Shard Ownership 未定义多 Key 原子性 | 单机协调器按固定顺序取得执行权；原子命令一次发布；Batch 不原子 |
| D09 | 事件 ID 的 96 位序号与 u64 字段不一致且可能跨库/重启冲突 | 复合 ID 为持久 stream_id + db + shard + u64 sequence |
| D10 | Key Version 可能删除后复用 | generation 加 revision，过期任务校验身份、版本与期限，避免旧任务误删 |
| D11 | 所有事件同等可靠，但 D13 给 TTL_CHANGED 强制 Fast 例外 | **有意修订原 D13**：六类事件统一跟随实例模式；频率优化不能隐式降低可靠性 |
| D12 | 可靠事件与普通缓存恢复混在一起 | Reliable 仅保证已 fsync 事件在保留期内恢复；缓存值/TTL 首版不恢复，不补发停机过期 |
| D13 | Snapshot / 数据 WAL 虽可选，但没有恢复格式和一致性设计 | **收紧首版范围**：数据持久化、SAVE / NOSAVE 延后 v1.x；事件 Journal 独立实现 |
| D14 | 每组保留、有限重试和死信有配置但无查询/重放接口 | 首版统一 7 天保留，明确超期错误，有界持续重投；每组保留及死信延后 |
| D15 | events.mode 和多个资源配置可随时热改 | 首版仅 log.level 热改；模式、资源和其他静态项重启生效，避免未定义的切换竞态 |
| D16 | ASYNC 清库“立即返回”却没有可见性定义 | 返回前完成逻辑清空和必要事件提交；仅物理回收异步 |
| D17 | MDEL/MEXISTS 与 DEL/EXISTS 重复 | 保留已有多参数 DEL/EXISTS，减少别名；DEBUG 命令不作为生产接口 |
| D18 | 时间轮、紧凑索引和大量 crate 被当作前置条件 | 先最小正确实现，度量后拆分/优化，不先创建空模块和复杂内存设施 |
| D19 | 配置同时列出未设计的持久化、DLQ、日志轮转等接口 | 仅保留首版有契约的配置；日志交给 stdout/stderr 和外部收集系统 |
| D20 | “2 倍 Redis”和“零事件丢失”容易被理解为现状或无条件承诺 | 吞吐为研究目标；可靠性严格限定为已提交记录及保留窗口，比较须语义一致 |

## 格式冻结与实验门槛

以下问题可以在既定边界内通过实验解决，不应伪装成已完成结论：

| 项目 | 当前方向 | 完成条件 |
|---|---|---|
| 网络字节格式 | protocol 中的版本 1 编码已冻结 | 已有共享黄金/错误向量和分段输入测试；后续语言继续复用并验证互操作 |
| Journal 磁盘格式 | 长度、校验、事务提交标记和检查点 | 明确字节布局与同步顺序，崩溃/截断/轮转用例后冻结；不能直接持久化 Rust struct |
| Shard 执行 | 所有者串行基线 | 正确性与同 Key 顺序通过后比较锁、所有者队列和读路径开销 |
| TTL 调度 | 可验证简单结构，保留时间轮方向 | 大量同刻过期、高频续期、远期期限与内存预算实测 |
| 索引与分配 | 标准结构原型 | 分离 Key/Value/索引开销，用 RSS 与受管字节证明紧凑化收益 |
| LRU/LFU | 采样近似 | 固定随机种子可测试；策略变化不能破坏写入原子性与事件 |
| 性能目标 | 同条件比较 Redis 8 的可比操作 | 发布原始环境、负载、吞吐、延迟分位及方差；未达目标也如实记录 |

若未来要求“每一个计划到期的 Key，即使停机或崩溃也必须生成通知”，必须重新设计并持久化期限及生命周期状态；这属于新的可靠定时能力，不能仅通过改文案扩展 Reliable 保证。

## DEC-02：发行来源证明与验证器（2026-11-17）

所有者已选择 GitHub 构建来源证明。仓库 `921108257/ling` 为公开仓库，适用 GitHub 公共仓库的 attestation 支持；使用 GitHub OIDC 和公共 Sigstore 的短期证书，无需保管长期签名私钥。发布工作流以 SLSA v1 证明绑定包、每包 CycloneDX 1.6 SBOM、审计报告及校验清单，并上传离线 `PROVENANCE.sigstore.json`。证明绑定工作流执行身份与摘要，不证明软件无漏洞。

备选 cosign keyless 使用同类身份与透明日志机制，但增加另一套 CLI／策略维护；minisign 的离线验证更简单，却需要私钥保管、备份和吊销策略。本轮选择与现有 GitHub Actions 一致的机制。Windows Authenticode、macOS Developer ID 与公证属于 DEC-03，所有者确认本轮继续顺延，来源证明不替代这些平台签名。

更新器调用官方 GitHub CLI 2.97.0 或更高版本，使用随二进制内置的公共 Sigstore 信任根离线验签。固定仓库、OIDC issuer、`release.yml` 的完整证书身份、`refs/tags/v<目标版本>` 和托管 runner；验证后再次匹配声明的资产名与 SHA-256。不存在凭据、验证器不可用、错误身份／标签或任何验签失败均拒绝安装，不提供仅校验和降级开关。`--check` 只报告凭据是否提供及验证器是否可用，真正的密码学验证在下载后完成。

选择外部官方验证器，是为了复用已维护的 Sigstore 验证实现；不把仍需单独审计的 Rust Sigstore 实验库及其密码学／证书依赖并入服务器。代价是安装者需要预装可信来源的 `gh`，该可执行程序本身属于本机信任边界。验证子进程清除 GitHub token、使用空配置目录、关闭遥测和更新通知，限制输出与执行时间。下载客户端仅向固定 GitHub API 发送 `LING_GITHUB_TOKEN`，API 不跟随重定向，下载 CDN 不携带令牌。

`crates/server/src/update/trusted-root.json` 于 2026-11-17 经 `gh attestation trusted-root` 的 TUF 校验获取，选取公共 Sigstore 根，SHA-256 为 `3c2cc7f357dc064ec527fdcd78da6e9245c21a381e1abaa0f2b62b186bcac1a1`。保留旧和新 CA／日志密钥及有效期；计划轮换时先发布同时信任新旧根的版本，至少跨一个版本周期再停用旧签发根。紧急吊销不能只靠新根替换：停止受影响发布、撤销／限制仓库工作流权限，并让旧客户端通过独立渠道获取新版本。未知新根会使旧客户端安全失败，不能自动接受下载包附带的信任根。

参考：[GitHub attestation action](https://github.com/actions/attest)、[官方验证命令与离线参数](https://cli.github.com/manual/gh_attestation_verify)、[公共 Sigstore 根](https://github.com/sigstore/root-signing)。

## 0.1.6 构建与依赖决定（2026-11-17）

仅在 CI 固定 Rust 1.94.0，不添加影响所有开发者的 `rust-toolchain.toml`。最初 Rust 1.85.0 对旧依赖检查通过；本轮审计发现 `zip 2.6.1` 处于多份 RustSec 公告范围，升级到 9.6.1（仅启用 deflate-flate2）后最低版本提高至 Rust 1.88，workspace 和 CI 一致调整，不保留无依据的审计豁免。

采用默认开启的 `self-update` feature；源码构建可关闭，`ling update` 返回 `LOCAL_UPDATE_DISABLED`，协议和服务行为不变。官方包保持开启。依赖数量与两种构建体积由 `scripts/measure-update-deps.py` 记录，不用依赖数量替代安全结论。构建输入固定提高可复核性，不等于跨主机二进制逐位可复现。

## 0.1.7 客户端与 CLI 范围决定（2026-11-17）

本轮维护可独立实现的协议、共享字节与会话向量、三语言参考客户端和 CLI 契约。Go 路径保持 `linger.local/cache`，Java 保持 JDK 17 直接编译，Rust 保持 workspace 路径依赖；不认领公共 SDK 发包，因此 DEC-04 至 DEC-06 继续作为可选发包前的决定，不代为选择坐标或占用名称。

7.1 行编辑与持久历史本轮不做：现有标准输入既服务交互命令也服务 Batch 和订阅 ACK，没有此次缺陷所需的能力缺口；新增库还需验证 Windows 控制台、历史中凭据处理与七语言帮助。7.2 机器可读输出本轮不做：当前任务是修复确认和会话契约，尚无明确的外部解析需求，保留现有无损类型文本。未来如提供格式，先定义类型标签、完整 Int / UInt 和 Bytes 的往返契约，再选择依赖。未新增相关选项，无需为可选功能扩充帮助。

不加入自动恢复或发送后只读重试白名单。现有池失效租约释放后可在后续租用重建固定库连接，失败中的请求不重放；订阅由调用方显式恢复并核对流身份。套接字选项本轮只据源码记录，不宣称延迟收益，专项 A/B 测量仍属后续工作。

## 0.2.0 执行模型评审（2026-11-18）

本轮先合入契约，再实现并验证。协议 v1、错误码与 Journal v1 不变。评审依据包括 0.1.5 原始结果、当前提交路径及订阅状态机；实现完成和测量结果单独记录在版本计划与 testing.md。

| 项目 | 决定与依据 |
|---|---|
| 组提交 | 不实施。0.1.5 的 7.1 已推迟；三次 Reliable 数据的 `timing_enabled=false`、fsync 采样数为 0，仅有 4 连接/4 分片，没有 fsync 占比或互不相交事务的并发证据。保留逐事务同步与 `group_commit_ms` 的预留预算语义，不从整体吞吐推断收益。 |
| 连接流水线 | P1 顺延。既有数据只有深度 1，缺少规定的深度 1/8/32 与连接 4/32 对照。维持每连接串行及当前帧预算，避免在无测量时增加调度、屏障和在途字节预算。 |
| 订阅提交唤醒 | 补齐基线后实施。现有三次 3 秒 Reliable 场景仅确认 302/303/302 次 ACK，与 10 ms 派发限制相符；新工具先测 0/1/100 空闲订阅、积压交付、CPU 与 PING 尾延迟。增加 `events.notification_enabled`，默认 true；false 保留原 10 ms 派发作为兼容和同二进制对照。 |
| 连接拒绝 | 实施明文 TCP 的有界拒绝帧：连接上限已满时尝试在 50 ms 内写出 ID=0 的 `ERR_BUSY`，随后关闭；同一时刻最多一个拒绝写入任务，额外超限连接直接关闭。TLS 在握手前仍直接关闭，不向 TLS socket 发送明文，也不为超限连接新增握手资源。 |
| TLS 握手期限 | 保持复用 `server.shutdown_timeout_ms`，补半开握手回收契约，不增加配置键。 |
| Windows Reliable | 选择正式不支持矩阵，保留启动前 `ERR_CONFIG_INVALID` 与无目录副作用。未完成平台的创建、替换、故障恢复与持久化验收，不能宣称支持。安全标准库目录打开加同步在本机可成功，不能据此推导断电持久性，也不能宣称必须放宽 unsafe；本轮不触发 DEC-11。 |
| 淘汰并发 | P2 不实施。0.1.5 的 7.2 已推迟，尚无三种限额配置的锁范围对照。 |
| 命名组管理 | P2 顺延。v1 组记录只有完整快照，`expired` 不是删除。追加删除需要格式变更；完整压缩省略组虽可能保持 v1 字节格式，仍需单独设计活动租约、同名重建和失败契约。 |
| 证书热加载 | P2 不实施。没有本轮必须解决的轮换需求或相应验收数据，`CONFIG RELOAD` 继续只修改日志级别。 |

订阅通知只是重新检查的信号，不能携带未提交事件。事件发布、成功 ACK、断开释放租约、保留范围改变以及 Journal 故障才唤醒；没有状态改变的维护与普通交付不向所有订阅广播。订阅先登记通知，再在同一事件锁下原子返回 `event / retry_at / more`（事件、最早重投期限、是否还有过滤历史）。只有扫描有进展且未追平时 `more=true`，只继续当前订阅；预算拒绝返回 false 并等待变化，避免空转。先发 SUBSCRIBE 成功响应，再发 EVENT。

重投期限沿用既有语义：恢复的未确认记录立即可取；无所有者记录等待 `sent + retry_interval_ms`；有所有者记录等待 `sent + max(retry_interval_ms, consumer_timeout_ms)`。无 pending 时不设置周期重投定时器。任务仍共享原有有界执行许可，关闭和取消释放租约；新增开关不改变 ACK、保留窗口或恢复保证。

## DEC-09：本轮验收环境安排（2026-11-18）

所有者指定可使用 WSL，并以强制关机进行故障测试。本轮 0.3.0 Preview 的环境与故障验收据此改为专用 WSL 发行版，记录宿主、WSL 内核、虚拟磁盘、文件系统和负载条件，只终止该测试发行版。2026-11-18 已导入专用 `ling-acceptance`，使用其 ext4 文件系统保存源码、二进制与 Journal；日常 Ubuntu 发行版不参与强制终止。强制终止结果标为 WSL 崩溃恢复，不能代替物理断电、设备易失写缓存或独立负载机证据；这些仍是后续稳定版的未验收边界。

同日所有者明确选择发布前 Fast、Reliable 各完成 72 小时压力验收，完成后才能发布 0.3.0，再立即扩大测试。每种模式的五种淘汰策略分段运行，每段 14 小时 24 分钟；段间新建服务和 Journal，不称为单进程连续 72 小时。严格值影子验证使用独立 noeviction 实例连续运行 72 小时，避免把正常淘汰误报为数据不一致。负载与通过标准先写入版本计划并提交，再开始正式计时。

0.3.0 发布完成后的大量测试采用仅记录策略：保存输入、种子、日志、复现步骤、影响和未决项，不在该测试阶段修复产品代码。发布前必要的正确性修复及既定发布门槛仍需完成；物理断电与目标环境多日验收未完成时明确保留，不以 WSL 结果改写历史事实。

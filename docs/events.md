# Key 事件与消费契约

> 状态：阶段 5 已实现 Fast / Reliable、六类事件、组、ACK、重投与保留；仍为预览原型，未做长期压力或性能验收。范围以 [architecture.md](architecture.md) 为准；落盘边界见 [persistence.md](persistence.md)。

## 模式与保证范围

| 模式 | 提交介质 | 断线与重启后的保证 |
|------|----------|--------------------|
| 事件禁用 | 无 | 不生成事件 |
| Fast（默认） | 有界内存队列 | 尽力投递；断线、溢出和重启均可能丢失事件 |
| Reliable | fsync 提交的 Event Journal | 已提交事件在保留窗口内可重放，至少一次投递 |

六类事件均遵循所选模式，`KEY_TTL_CHANGED` 没有隐含的 Fast 例外。只是不关心 TTL 变更的消费者可以过滤它，但过滤不改变事件本身的持久性。

Reliable 不等于缓存值持久化，不承诺恰好一次业务处理，也不承诺无限保留。尚未提交的到期记录、停机期间到期以及冷启动消失的缓存条目，不保证补发通知。SDK 应在处理成功后 ACK，并使业务处理可幂等。

## 事件类型

| 类型 | 触发条件 |
|------|----------|
| `KEY_CREATED` | 当前不存在的 Key 被成功创建 |
| `KEY_UPDATED` | 已存在 Key 的值实际变化，包括集合局部修改 |
| `KEY_EXPIRED` | 期限已到，被确认为过期；包括设置为立即过期 |
| `KEY_DELETED` | 主动删除、清空或移动/重命名的来源被移除 |
| `KEY_EVICTED` | 按内存淘汰策略移除仍活跃的 Key |
| `KEY_TTL_CHANGED` | 已存在 Key 的期限被设置、改变或移除 |

提交前明确拒绝、条件不满足以及状态完全相同的写入不产生事件。提交结果不确定的请求可能已经产生事件，不能把超时或磁盘同步错误解释为必然未执行。创建时附带 TTL 仅产生创建事件；更新同时改变 TTL 时，值事件在前、TTL 事件在后，作为同一事务提交。

重命名或跨库移动产生来源删除及目标创建/更新事件，身份反映各自数据库和 Key。复制仅改变目标。覆盖已有目标时用 `KEY_UPDATED` 表示替换，不额外伪造目标删除。`FLUSHDB` / `FLUSHALL` 为每个活跃 Key 产生删除事件；已经到期的 Key 保留过期原因。

事件只描述提交的变更事实，不携带旧值或新值。事件到达时再 `GET` 可能看到更晚版本或不存在，不能据此恢复当时 Value。

## 事件身份与字段

| 字段 | 契约 |
|------|------|
| `event_id` | 复合值 `(stream_id: u128, db: u16, shard: u32, sequence: u64)` |
| `event_type` | 上表六种类型之一 |
| `key` | UTF-8 Key，与命令中的 Key 规则一致 |
| `generation` | Key 生命周期身份：进程 epoch 与进程级全局创建计数 |
| `revision` | 此 generation 内的状态修订号 |
| `timestamp_ms` | 服务端事件记账时的 Unix 毫秒，仅用于观察 |

`stream_id` 属于整个事件日志目录，并持久化保存。每个 `(db, shard)` 的 sequence 单调递增；恢复时从已提交日志延续，不复用。清空缓存、重启或删除 Key 不重置 sequence。目录丢失或新建目录产生新的 stream_id，不能假装继续旧流。

新建生命周期 revision 从 1 开始；一次命令同时改变值与 TTL 也只递增一次，两条关联事件携带相同最终 revision。删除、过期、淘汰携带该生命周期最后的 revision，不为终结另加版本。普通 SET 覆盖已有活跃 Key 延续 generation；COPY / MOVE / RENAME / SWAPDB 的目标分配新 generation，存在目标仍按 UPDATED 描述替换。

Fast 的 stream_id 在进程启动时新建，不提供跨启动连续性。重复投递必须使用原 event_id，不生成新 ID。sequence、revision、创建计数溢出均显式失败，不能回绕。

同一 `(db, shard)` 内事件按提交顺序交付。跨 Shard、跨数据库不提供全局消费顺序；事务原子提交也不表示消费者能在一条消息中同时看到全部事件。

## 生成与发布

Reliable 模式下，普通变更先验证，再将所有事件写入同一原子 Journal 事务，完成 fsync 后发布值变更及事件并返回成功。涉及多个 Shard 的命令由协调器取得固定顺序的执行权，使用同一物理 Journal 事务，不采用互相独立的“先写一半”提交。Fast 在内存发布，事件禁用时不生成事件。

期限到达时逻辑不可见可以早于 Journal 提交；过期事件提交成功之前仍保留记账所需信息。细节见 [ttl.md](ttl.md)。

推送只读取已提交事务，不能发送 prepare、截断尾部或未完成的记录。请求超时、响应丢失可能发生在提交之后，调用方结果不确定；请求 ID 仅匹配响应，不提供写入去重。

## 订阅连接与组

```text
SUBSCRIBE pattern [pattern ...] [GROUP group]
ACK event_id
UNSUBSCRIBE
```

订阅使用专用连接，与普通命令连接分开。连接在订阅前选择数据库；进入订阅状态后不得执行 `SELECT` 或普通数据操作。一个订阅连接最多绑定一个组身份，`ACK` 只作用于这个身份。

pattern 匹配所选数据库中的 UTF-8 Key；通配规则与 `SCAN MATCH` 一致。多个 pattern 取并集，同一事件不因匹配多个 pattern 被重复加入一次交付。跨库消费需要独立订阅。

省略 `GROUP` 创建临时会话，从当前提交尾部开始。临时会话断开即销毁，不提供断线恢复；Reliable 也不会把临时会话自动变成持久组。

命名组在 Reliable 下持久化。首次 `SUBSCRIBE ... GROUP group` 原子记录当前各 Shard 的尾部位置，从之后的事件开始；重连沿用该组 ACK 状态。Fast 中命名组只在当前进程内有效。

同一个组绑定首次选择的数据库及去重后的 pattern 集合，后续消费者必须完全匹配，否则返回错误。组内连接分担事件，不同组独立消费同一事件流。组身份不是每连接一个新的消费位置。

`UNSUBSCRIBE` 关闭当前订阅会话，不删除命名组及其确认状态。首版不提供在线修改命名组过滤条件、删除组或部分退订；需要新过滤条件时使用新组名。

## ACK、重投与顺序

每个组按 `(db, shard)` 维护连续已确认水位，以及水位后的乱序确认集合。只可确认曾经交付给该组的事件；无关组、其他 stream_id 或未来序号的 ACK 返回错误。已确认事件的重复 ACK 幂等成功。

不匹配 pattern 的记录由服务端确定跳过，不等待业务 ACK。只有所有较早的匹配记录都确认后，连续水位才能前移；不能直接把最大 ACK 序号当成恢复位置。

Reliable 命名组的 ACK 状态需 fsync 后才返回成功。ACK 提交前断线或崩溃可能重投已处理事件；ACK 已提交则恢复后沿用。临时会话的 ACK 只更新内存交付窗口，不持久化，也不提供断线恢复。组内重新分配或超时重投不会改变 event_id。

`events.consumer_timeout_ms` 控制未确认交付的租约，`events.retry_interval_ms` 控制重投间隔。连接失效或租约到期后可以交给另一消费者；旧消费者晚到的有效 ACK 按组幂等处理。首次发送按流内顺序，重投可能与新交付交错；业务完成顺序不保证。

首版不设“重试若干次后自动确认”，不实现死信队列。失败事件持续按有界窗口重投；单个消费者不能无限占用内存，运维通过积压指标定位处理失败。

## 保留与容量

`events.retention_days` 默认 7 天，是已提交事件能够恢复的最长时间窗口，不是保证每个组都一定消费完成。首版统一保留期限，不提供每组独立延长。当前按完整事务前缀清理，墙钟回拨时保守保留后续事务以避免流内缺口。维护约每秒检查，期限决定清理资格，不承诺物理删除的精确时点。

清理可以移除超过期限的事件，即使某组尚未确认。若恢复位置或未确认空洞已落到保留范围之外，返回 `ERR_OFFSET_EXPIRED` 并停止该组交付，不能静默从最新位置继续。

首版恢复方法是调用方明确使用新组名，从创建时尾部开始。创建新组表示接受缺失区间，服务端与 SDK 不自动执行。

`events.buffer_bytes` 限制内存事件缓冲；`events.max_pending_events` 限制单组水位之后尚未消除的交付窗口，包括未 ACK 记录和因较早空洞而保留的乱序 ACK。所有消费者、所有逻辑流合计占用该窗口，防止先不确认一条再无限确认后续记录造成元数据增长。窗口满后暂停该组新推送，继续允许重投与补齐 ACK，不代表自动删除磁盘事件。

`event_journal.max_bytes` 限制物理日志总容量，包含事件和消费元数据。达到上限且无法按保留策略清理时，Reliable 拒绝需要产生事件的新写入并报告背压；不能提前丢弃仍在保留期内的事件。自然过期继续逻辑不可见，记账等待可用容量。

## 错误与观测

日志不可写、校验损坏、订阅身份冲突、Offset 过期必须分别可辨识。Fast 的丢弃计数与 Reliable 的 Journal 同步错误计数分开，不能统一显示为“已发送”。

事件存储的 `stats / group_stats` 提供提交及按类型事件数、Journal 字节数、最老保留时间、组确认水位、最老未确认交付年龄、窗口项数、重投、Fast 丢弃及 Journal 同步错误数。年龄仅指本次进程已发送的交付；恢复后的租约年龄未知，返回空值。`INFO events` 暴露分类统计及消费组详情；Prometheus 暴露固定分类与聚合计数，不以组名或 Key 建立标签。

## 必需验证

- 六类事件在 Fast / Reliable 下遵循同一模式，提交前明确拒绝的变更不发布事件。
- 同流排序、跨 Shard 原子提交、重命名/清空事件、重复投递 ID 稳定。
- 多消费者分摊、多组隔离、过滤重叠去重、乱序 ACK 及 ACK 持久化前后崩溃。
- 断线恢复、租约重分配、旧消费者晚 ACK、组过滤条件不一致、伪造或未来 ACK。
- 保留超期显式报错、缓冲/磁盘上限背压、Fast 丢弃计数、重启 stream/sequence 延续。

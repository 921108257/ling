# 事件持久化与故障恢复

Reliable 通过同步 Journal 保存事件及消费元数据。缓存值与 TTL 始终只在内存中，重启后不恢复。消费方式见 [事件与消费](events.md)。

## 持久化范围

持久化对象是 Reliable Event Journal 以及维持消费连续性所需的元数据。缓存 Value、内存索引和 TTL 不做 Snapshot / 数据 WAL 恢复，重启后缓存为空。

当前 Reliable 实现面向支持文件及目录同步、原子替换的 Linux / macOS 文件系统。Windows 尚未实现对应的目录同步与替换持久化路径，Reliable 配置在文件操作前返回 `ERR_CONFIG_INVALID`；服务端和 CLI 的默认 Fast 模式仍可使用。不会通过省略目录同步或静默降级为 Fast 来绕过这一限制。

不支持 `SAVE`、`SHUTDOWN NOSAVE`、缓存 Snapshot 或数据 WAL，也不提供从事件重建缓存的功能。

| 数据 | Fast | Reliable |
|------|------|----------|
| 缓存 Key / Value / TTL | 仅内存 | 仅内存 |
| 生命周期事件 | 有界内存队列 | 原子 Journal 事务 |
| 命名组定义与消费位置 | 仅当前进程 | Journal 持久化 |
| stream_id 与各逻辑流序号 | 当前进程有效 | 跨重启延续 |

没有缓存恢复意味着：已提交事件可以存在，而相关 Key 在重启后不存在；这是正常语义。Journal 不存完整 Value，不能通过重放事件重建缓存，也不合成“重启删除”通知。

## 提交保证

Reliable 必须在完整事务完成 fsync 后才能向客户端确认成功。恢复接受有效且有完整提交标记的事务；即使崩溃前未收到 fsync 返回或响应，完整事务也可能幸存，因此结果未知的请求仍可能恢复可见。当前每个事务直接 fsync，不主动等待合并；`group_commit_ms` 仅限定允许的最大主动等待预算，不改变提交保证。

普通数据变更的处理顺序：

1. 按 `(db, shard)` 固定顺序取得命令涉及的执行权，检查类型、条件、容量和参数。
2. 准备新状态和关联事件，预留发布所需内存；此时其他请求看不到新状态。
3. 将完整事件事务追加到服务器统一的物理 Journal。
4. 完成 fsync，使提交记录和事务内容一起持久。
5. 整体发布相关内存状态和事件，释放执行权，再返回成功。

跨 Shard 命令使用同一个 Journal 原子事务，不把每个 Shard 的独立成功当成整体成功。物理 Journal 内可以交错存储多个 `(db, shard)` 逻辑流，但恢复仅暴露完整提交的事务。

协议和命令层的原子性不能由客户端重复调用模拟。实现应在发布前预留必要资源，避免写盘已经成功之后才因正常内存分配失败而只发布一半。

TTL 到期是例外的可见性边界：时钟已使条目逻辑不可见，Journal 负责记录其终结事实；提交之前保留记账信息，不能先释放再补写。参见 [ttl.md](ttl.md)。

已提交但尚未发送响应时崩溃，事件恢复可见、缓存为空，客户端可能得到超时。不能撤回已提交事件，也不能宣称该超时请求一定未执行。SDK 不自动重试非幂等写操作。

## 日志内容与目录

日志至少包含：

- 持久化格式版本、stream_id 和识别各段的元数据。
- 首次建立日志时的数据库数量及实际 Shard 数量，用于保持历史逻辑流坐标稳定。
- 完整事件事务及提交标记，事务内各事件的逻辑流及序号。
- 命名组的数据库、pattern 集合、初始尾部位置。
- 各组 ACK 状态：连续水位及必要的乱序确认空洞。
- 保留边界和恢复序号所需检查点。

记录使用长度边界及校验，能够区分完整记录与写入中断尾部。磁盘格式独立于网络协议和 Rust 结构体内存布局，格式版本见下文。

`event_journal.dir` 独立于缓存数据目录概念；首次创建时产生新的 stream_id。进程需独占这个目录，禁止两个服务同时写入。目录锁失败直接拒绝启动。

既有目录启动时，数据库数量和实际 Shard 数必须与元数据一致，否则拒绝启动；自动 Shard 数在不同 CPU 环境解析出不同值也不能复用。需要改变拓扑时使用新目录和新 stream_id，保留旧目录供历史恢复，不静默迁移或丢弃历史。

段轮转、检查点替换和旧段删除必须按持久化顺序执行。涉及新文件名或原子替换时，需要完成相应目录同步；不能只同步文件内容就假设目录项已经稳定。

## 磁盘格式 v1

所有整数为大端，字符串为 u32 字节长度加 UTF-8。目录含 `LOCK`（操作系统独占锁）、`journal.lgj` 和仅压缩期间存在的 `journal.next`。不写 Value 或 TTL；不复用网络封套。新目录初始化文件及重命名均同步目录。

文件头为 `LGJRNL01`（8 字节）、版本 u32=1、stream_id u128、数据库数 u32、实际 Shard 数 u32、前述 36 字节的 CRC32 u32，共 40 字节。记录为 Payload 长 u32、Payload CRC32 u32、Payload、提交尾标 `LGCMT001`（8 字节）。Payload 首字节为类型：1=事件事务，2=消费组状态，3=检查点。事件事务为非零 u32 数量及事件序列；事件编码为 db u16、shard u32、sequence u64、类型 u8（依次 CREATED=1、UPDATED=2、EXPIRED=3、DELETED=4、EVICTED=5、TTL_CHANGED=6）、Key 字符串、generation epoch u128/counter u64、revision u64、timestamp_ms u64。

消费组 Payload 为标签 2、内部名称字符串（命名组前缀 `n:`，其后组名为 1—128 字节）、db u16、expired u8、pattern 数 u32 及字符串列表、进度数 u32 及每项 shard u32/origin u64/watermark u64/cursor u64、pending 数 u32 及每项 shard u32/sequence u64/acked u8。Bool 仅允许 0/1；pattern 排序去重，进度按 shard、pending 按 (shard, sequence) 排序。租约不恢复。检查点为标签 3、tails 和 floors 两张表；每表为 count u32 及排序的 db u16/shard u32/sequence u64。检查点只可作为文件首条记录，重放从 floors 连续验证至 tails 并继续，不接受重复或跳号。每条记录最长 min(128 MiB, buffer_bytes / 2)，长度在分配前校验；CRC 或完整尾标错误均拒绝恢复。只允许截断文件末尾不完整的记录，不猜测完整坏记录是否提交。未知版本或标签拒绝启动。

每次事务直接 fsync，不主动等待合并；group_commit_ms 是允许的最大主动等待预算。压缩以检查点、存活事件事务和最新消费组状态写入 journal.next，fsync 后原子替换并同步目录；替换失败后进入全局故障状态。一个有效日志占 max_bytes 的至多一半，另一半预留原子替换；其中八分之一总容量另留给控制记录，事件追加不能侵占；最新组快照合计（含记录边界）≤ max_bytes / 16，完整拓扑检查点预留满足 28 × databases × shards + 65 ≤ max_bytes / 16，保证状态替换与 ACK 预算。资源上限不足显式背压，不缩短保留期。消费从磁盘顺序读取，避免把全部 Reliable 事件载入内存。

消费组使用运行时的物理记录游标，从已验证边界继续扫描；单次扫描遇首个匹配事件或字节预算即停止。同一事务未交付的后继仍可重访，由各流逻辑 cursor 去重。恢复和压缩均将物理游标重置到文件头之后，物理偏移不持久化；ACK、租约和保留位置独立保存。

后台每秒检查首个保留事件是否可能达到统一保留期限；未达到或日志无事件时，不扫描和重写整个文件。达到期限才检查完整事务前缀并压缩；事件或控制记录容量不足仍独立触发压缩，以回收历史控制记录，不能绕过保留限制。故障日志保持明确报错，不因本轮无到期内容而隐藏故障。

## 启动与恢复

1. 校验配置、目录所有权、格式版本与 stream_id，取得目录独占权。
2. 读取已提交检查点及后续日志，验证长度、校验和与事务完整性。
3. 还原组定义、确认状态、保留边界和各逻辑流的下一个序号。
4. 丢弃可明确识别的未提交尾部，保留所有完整已提交事务。
5. 建立空缓存和新的 Key generation 进程 epoch，开始接收连接。

若中部损坏或无法确认某记录是否已提交，应拒绝启动并报告损坏位置，不能跳过后继续宣称可靠。恢复中“截断尾部”只适用于已识别的未提交末尾，不是通用修复开关。

恢复完成之前不接受业务写入或消费，防止新请求与未恢复的序号、组位置竞争。组恢复请求若已经落后于保留边界，应明确报 `ERR_OFFSET_EXPIRED`。

删除或遗失目录后，新实例属于新事件流。旧 event_id / Offset 不能在新流中解释；客户端必须显式处理流身份变化。副本复制、备份恢复和跨主机自动接管不在当前版本范围。

## ACK 与消费元数据

命名组创建和命名组 ACK 都是需要提交的 Journal 操作。首次订阅只有在组定义及初始位置完成 fsync 后才确认创建成功；命名组 ACK 也只有在状态落盘后才返回成功。临时会话的 ACK 只确认本次内存交付，不写消费位置。

乱序 ACK 不允许跳过未确认事件。检查点必须保存足以恢复空洞的数据，或者仅安全推进连续水位；不能通过检查点丢弃仍需要重投的内容。水位后的未确认记录与稀疏确认集合共同受交付窗口上限约束，不能通过持续确认后序事件绕开内存预算。

组内投递租约属于运行时状态，重启后未确认事件可重新分配。恢复无需保留失效连接身份；必须保留组的消费边界。

临时订阅不需要持久化消费位置，即使服务处于 Reliable。其已收到事件由 Journal 保留，不代表临时订阅断线后有可恢复会话。

## 容量与保留

`events.retention_days` 是事件保留期限，默认 7 天。已过期内容可以清理，与组是否消费完成无关；清理后必须保留可判断 Offset 过期的边界信息。

`event_journal.max_bytes` 是日志目录容量上限。预算包括事件、ACK、检查点、段轮转临时空间和提交记录；不能只统计 Payload。

Journal 为 ACK、消费组检查点及轮转预留独立空间；事件写入不能占用该预留。

接近上限先停止接受新的产生日志的缓存变更；现有消费可以继续释放在途压力，按期限允许清理的段才可删除。不能为了新写入静默缩短保留窗口。

Fast 的内存缓冲上限与 Reliable 的磁盘上限分别统计。磁盘容量、组内在途窗口和缓存内存限制是不同约束，错误响应和指标必须能区分。

## 配置与模式切换

| 配置 | 作用 |
|------|------|
| `events.enabled` | 是否生成 Key 事件 |
| `events.mode` | `fast` 或 `reliable` |
| `events.retention_days` | 已提交事件的统一保留期限 |
| `event_journal.dir` | 持久化事件及消费状态的目录 |
| `event_journal.max_bytes` | 目录容量上限 |
| `event_journal.group_commit_ms` | 最大主动等待预算；当前逐事务同步，不主动等待 |

Reliable 不提供 `fsync=none` 配置。底层文件系统及存储设备必须支持所需同步语义；仅 write 成功不能作为持久化成功。

`events.mode` 只在重启时生效。已有 Reliable 目录禁止以 Fast 模式复用或自动删除，避免用户误以为旧消费历史仍可恢复。需要 Fast 时显式使用不同运行配置并保留原目录。

启用 Reliable 必须使用可写的有效目录及非零有效容量。配置校验在监听端口前完成，不能启动后才静默退回 Fast。

## 失败与关闭

容量或参数校验等明确发生于提交前的失败不发布普通变更。Journal 写入或 fsync 返回错误时，若无法证明事务未提交，应将请求结果标为不确定并停止相关写入；有效的完整事务可能在恢复时出现，不能声称该错误表示未执行。已提交部分不可回滚为“没发生”，实现必须区分提交前拒绝、提交结果不确定和提交后响应失败。

统一物理 Journal 部分写入或同步状态不确定时进入全局故障状态，暂停全部新日志追加及持久 ACK 成功响应，不能只冻结某一 Shard 后让其他 Shard 继续追加。受控恢复确认事务和尾部后才能继续；未确认前不得为同一过期事实分配新事件 ID 重试，避免重复原始事件。明确提交前的容量拒绝可在容量恢复后重试。

自然过期仍使 Key 不可见，但其待记账信息不释放，并阻止受影响 Shard 继续写入。磁盘恢复后可继续提交；进程在此期间崩溃，未提交部分仍不在可靠保证内。

优雅关闭停止接收新写入、排空已接受的提交、同步 Journal，再关闭消费连接。达到 `server.shutdown_timeout_ms` 可退出，但不把尚未同步的事务返回为成功。

当前版本不提供从损坏 Journal 自动重建、从事件恢复缓存、选择性跳过坏段或跨版本自动降级。明确失败比静默丢弃提交历史更符合 Reliable 的接口承诺。

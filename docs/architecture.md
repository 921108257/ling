# linger-cache-db 架构与范围

> 版本：v0.3 设计基线。阶段 1—6 已实现，阶段 7 稳定版验收待完成。本文由最初的 v0.2 项目规划整理而来；关键澄清记录见 [decisions.md](decisions.md)。

## 项目定位

linger-cache-db 是以 Rust 编写、独立部署、通过自定义二进制协议访问的内存缓存数据库。核心方向是 Remote-first、Shard Ownership 和 Memory-first。

目标是以清晰的强类型、原子命令、可验证的 TTL 和可选可靠事件，降低业务接入与并发处理成本。高吞吐、低延迟、低单 Key 内存占用是研发目标；阶段 3 的有限基础测量见 [testing.md](testing.md#阶段-3-基础测量)，不能据此宣称已超过 Redis 或已经可用于生产。

服务端不提供 Embedded API，不兼容 Redis 协议或命令行为。命令使用熟悉的名称，不意味着继承 Redis 的默认值、隐式创建、原子性或错误规则。

当前已有 Rust workspace、10 种共享 Value、协议编解码、固定分片引擎、TCP / TLS 服务、Rust / Java / Go SDK、CLI 与契约测试。支持隔离数据库、通用与容器命令、跨库复制 / 移动、遍历、清库 / 交换、五种淘汰策略及毫秒 TTL 生命周期；完整已开放清单见 [commands.md](commands.md)。支持六类事件、默认有界 Fast、可选同步 Reliable Journal、专用订阅、消费组、ACK、重投与保留清理，以及固定库连接池、普通 Batch、INFO / CONFIG / SHUTDOWN、日志和可选 Prometheus。构建与启动入口见 [README](../README.md)，本文计划目录仅按实际职责建立。

当前使用每个 (db, shard) 独占的有序索引与 Mutex，按全局顺序取得全部执行权后采样时间；预算 / 身份提交锁永远在分片锁之后取得，事件提交锁最后取得；消费者不反向取得引擎锁。候选结果通过类型、大小、响应、容量和身份检查后整体发布，多连接读不到原子命令中间状态。单 Key 读取可在独立分片并行；有每库 Key 配额的写入锁全库，启用淘汰且有限额的写入暂保守锁全实例，以避免逆序追加受害分片。此性能取舍需后续测量后再优化。

网络数据命令经有界许可进入 Tokio 阻塞线程池，任务数最多为 min(系统可用并行度, 连接数上限)，请求等待者受连接总数约束，另有最多一个后台维护等待者；不按数据库 × 分片创建线程。每连接仍逐条执行，保持屏障及接收顺序；排队超时只在执行前返回 ERR_BUSY，已开始的命令不能以超时宣称回滚。关闭期限取消连接，但已开始的阻塞命令仍会完成。异步清库使用单回收线程和容量为 1 的队列，满时同步释放；待释放数据持续计入受管预算，逻辑清空不等于 RSS 立即下降。

## 版本边界

“首版”指完成验收的第一个稳定版 v1.0，不等于第一个原型。中间版本必须标注实际支持的能力，不能用占位接口冒充实现。

| 能力 | v1.0 边界 |
|---|---|
| 部署 | 单进程、单节点服务器；TCP，可选 TLS 和密码认证 |
| 数据 | 10 种 Value，UTF-8 Key，默认 16 个隔离数据库 |
| 并发 | 固定数量 Shard；一个 Shard 一个明确所有者；同机跨 Shard 协调 |
| 命令 | [commands.md](commands.md) 的首版命令及错误语义 |
| TTL | 毫秒精度；相对、绝对期限及移除；读路径严格过滤过期值 |
| 事件 | 六类生命周期事件；默认 Fast；可选 Reliable、组消费、ACK、重投 |
| 持久化 | Reliable 事件及消费元数据；缓存值和 TTL 重启后不恢复 |
| 客户端 | CLI 优先；Rust、Java、Go；统一协议与契约用例 |
| 资源与运维 | 有界请求/队列/内存/日志；noeviction、采样 LRU/LFU、random、ttl-first；日志与指标 |

v1.0 明确不包含：

- Redis 兼容、Embedded API、SQL、Lua 或其他服务端脚本。
- 多节点集群、复制、跨节点事务、自动故障转移、分片迁移及动态修改 Shard 数量。
- 用户自定义多命令事务；普通 Batch 只减少网络往返。
- 缓存数据 Snapshot / WAL 恢复、`SAVE`、持久定时任务或停机期间 TTL 补发。
- Idle / Sliding TTL、TypeScript SDK、复杂 ACL、在线扩缩数据库数量。
- 死信队列、每组独立保留期限、在线切换 Fast / Reliable、订阅组在线改过滤器。

其中缓存恢复、TypeScript、扩展 TTL 等可在后续版本单独设计；“后续”不表示已承诺发布时间。

## 数据和客户端模型

全部 10 种类型都可直接存为顶级值：Null、Bool、Int、UInt、Float、String、Bytes、List、Map、Set。List / Map 可递归嵌套；Set 仅含标量。类型严格区分，默认集合深度不超过 8。

Key 为非空 UTF-8；默认数据库 0，默认数据库数量 16。数据库编号在协议和事件中使用 u16，数量上限 65,536；这是编码边界，不代表建议创建如此多数据库。

CLI 直接复用 Rust SDK，是优先交付的参考客户端。Java / Go 原生实现同一网络协议，不要求 JNI / cgo。规范定义语义，CLI 和所有 SDK 接受同一套契约验收；不能让 CLI 的偶然行为成为新协议。

所有客户端负责类型编码、连接、认证、选库、请求匹配、超时和订阅；原子数据修改由服务端完成，不能用 SDK 读改写代替。

## 组件与数据流

```text
CLI ── Rust SDK       Java SDK       Go SDK
          └──────────────┬──────────────┘
                      TCP / TLS
                          │
            网络层：连接、限流、读写背压
                          │
            协议层：帧校验、Value 编解码
                          │
            调度层：数据库路由、顺序、协调
                          │
           DB 0 ... DB n，各自独立 Shard 状态
                          │
       Shard 所有者：索引 / Value / 内存 / TTL
                          │
         事件层：逻辑事件流 / 订阅 / ACK
                          │
      Reliable 可选：统一物理 Journal 与组提交
```

每个数据库拥有自己的 Shard 状态，内存索引和 Key 命名空间不共享。执行线程可以服务多个数据库的 Shard，禁止按“数据库数 × Shard 数”无条件创建专属线程。

网络层不直接修改索引；协议层不决定 TTL；SDK 不决定事件是否已提交。模块边界先体现在代码所有权与接口，不要求第一天创建全部 crate。

## 并发与原子性

路由为 `hash(key) % shard_count`。哈希函数与种子是进程内部实现细节，客户端不路由到 Shard。Shard 数量启动时确定，运行中不可修改。

首个正确性实现优先采用所有者串行处理该 Shard 的读写；原型可使用清晰的锁。异步任务数量不等于 CPU 并行度。只在基准证明读队列或锁为瓶颈后评估快照读、读写锁或其他结构。

单 Key 命令原子执行。`MSET`、`RENAME`、`COPY`、`MOVE`、集合运算及清库等涉及多个 Shard 的命令，也须遵守各自声明的一致性，不能默认为部分成功。调度器按 `(db, shard)` 固定顺序取得全部执行权，先完成参数、类型和容量校验，再整体发布状态。读操作同样遵守执行权，不能看到多 Key 写入的中间状态。

全库操作可阻塞涉及数据库；v1.0 不保证这类操作低延迟。`FLUSHDB ASYNC` 的 ASYNC 只指后台释放物理资源，逻辑清空和事件提交仍须完成后才返回。

Reliable 下，一条原子变更的所有事件写入同一个物理 Journal 事务，fsync 完成后发布。逻辑事件流按 `(db, shard)` 排序；统一物理文件不对外承诺全局消费顺序。当前逐事务 fsync，未主动聚合；消费顺序扫描磁盘，保留维护每秒检查并原子替换压缩，尚未做吞吐优化测量。该方案存在协调和磁盘瓶颈，必须测量，不能一边保证原子性一边省略协调成本。

当前服务端及三种 SDK 均在单连接内串行执行；独立连接可在不同 Shard 并行，由有界连接池向客户端提供并发。协议 Request ID 保留响应匹配能力，尚未实现单连接并行多路复用。AUTH、SELECT、QUIT 是连接屏障。普通 Batch 的子命令按输入顺序独立成功或失败，不具有整体回滚能力。

## TTL 与身份

读路径根据已接受的期限判断是否过期，不依赖时间轮是否及时运行。逻辑不可见与物理回收是两个时点。

每次创建拥有新的 generation，同一生命周期内变化递增 revision；TTL 任务携带 generation、revision 和 deadline，执行前全部校验。删除后重建同名 Key 不能被旧任务删除。

相对 TTL 使用单调时钟；绝对时间在执行时换算为期限，之后系统时钟校正不改变已经接受的期限。Unix 到期时间用于查询和观测，不作为后台调度唯一时钟。

阶段 4 使用全实例有序到期索引，每个有期限条目至多一项，与状态修改在预算提交锁下同步替换；续期不积累历史任务。维护先在提交锁内复制最早候选并释放锁，再取得目标分片执行权，重新观察时间并核对完整身份和双期限；不持提交锁等待分片。单个后台循环与请求共享有界执行许可，每轮最多检查 ttl.maintenance_budget 个候选，轮间等待 1 毫秒，不承诺回收延迟上限。此共享索引取舍保持现有锁序，按 Shard 拆分和分层时间轮均留待测量后评估。

## 事件与恢复边界

默认 Fast 使用有界内存队列，可能丢事件；丢弃必须有计数。Reliable 下六类事件均持久化，包含 `KEY_TTL_CHANGED`，没有暗含的可靠性例外。

Reliable 保证已 fsync 的完整事件，在保留窗口内可恢复、可重投。默认保留 7 天；落后于保留位置的消费者得到明确错误，不能自动跳过。

缓存值、TTL 与索引仍只在内存。重启恢复 Journal 和消费进度，但缓存为空。不承诺补发未提交的到期事件、停机期间到期事件，或为冷启动消失的 Key 产生删除事件。

事件 ID 由持久 stream_id、数据库、Shard 和流内序列构成。重投不改变 ID，重启不复用序列。ACK 与命名组状态在 Reliable 下同样持久化。

自然到期不会等待磁盘才变成不可见。Reliable 写入先逐项记账已锁定分片内的自然到期；这是独立的生命周期终结，不属于随后命令的新状态事务，避免大积压超过单事务预算而无法推进。Journal 失败时保留待记账信息，阻止受影响 Shard 继续写入，并报告错误；不能返回旧值或先回收再补写。

## 资源、安全与运维

请求、响应、嵌套、连接、在途任务、缓存内存、事件缓冲和 Journal 均有明确上限。达到上限时产生可识别错误或背压，不允许无界队列。内存限制是逻辑预算，不是承诺进程 RSS 精确等于配置值。

默认 noeviction，达到限制拒绝扩大内存的写入。其他策略按样本或候选集选择受害者，淘汰也是正常状态变更，需要生成相应事件。实现必须先预留预算，不能为一次最终失败的写入提前删除无关 Key。

默认监听回环地址，认证和 TLS 可选。启用认证时空密码非法；配置查询与日志隐藏凭据。数据库编号是命名空间，不是授权边界。Rust 使用 rustls，Java 使用 JSSE，Go 使用 crypto/tls，验证证书与服务端名称，可选客户端证书认证。

INFO 与可选 Prometheus 指标覆盖请求、延迟、内存、TTL、事件和日志；禁止把 Key、Value 或密码作为指标标签。运行时仅支持修改日志级别，其他配置重启生效。

## 计划目录与依赖方向

```text
Cargo.toml                 # 已建立 Rust workspace
crates/
  server/                  # 入口、配置与组件装配
  cli/                     # 交互与命令展示，依赖 Rust SDK
  types/                   # Value、Scalar、身份及核心错误
  protocol/                # 线上编解码，依赖 types
  network/                 # TCP/TLS 共享传输与证书验证，依赖 types
  engine/                  # 命令、Shard 状态、索引与内存预算
  ttl/                     # 可独立验证后再拆出
  events/                  # 流、组、投递
  persistence/             # Journal 与恢复
  scheduler/               # 所有者与跨 Shard 协调，按实际复杂度拆分
sdks/{rust,java,go}/
tests/{correctness,concurrency,chaos}/
benchmarks/
docs/
```

这是组织方向，不要求逐项创建空目录或空 crate。存储索引初期可在 engine 内；只有实际复杂度需要时再拆 storage。避免为共享一两个类型创建 common 杂物层，基础契约归 types。

基础类型不得依赖网络或服务端。协议与引擎通过类型化命令/结果连接；SDK 可依赖协议和类型，但不得链接服务端引擎形成隐含 Embedded API。Tokio 是网络运行时的优先候选，具体依赖版本在创建 workspace 时选择并锁定。

## 验收原则

先正确，再优化，再评价是否达到稳定版。阶段门槛见 [roadmap.md](roadmap.md)。

性能比较必须使用相同硬件、系统、负载和持久化语义，保留原始结果。与 Redis 8 的比较只选语义可比的操作；“GET/SET 吞吐达到两倍”是研究目标，不是发布承诺，Reliable 不能与对方无持久化模式直接比较。

任何优化不得破坏类型、TTL 可见性、原子性与事件提交边界。没有实测数据前，不强制使用自定义分配器、无锁结构或专门读副本。

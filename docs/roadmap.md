# 实施路线与阶段验收

> 状态：阶段 1—7 已完成本机交付与验收，稳定版发布仍需目标部署环境评估。阶段按依赖排序，不代表发布日期或固定工期。

## 推进方式

先做能够端到端验证的小切片，再扩展类型、并发和可靠性。每阶段只建立实际需要的模块，避免先创建全套空 crate。阶段完成以契约证据为准，不能只看接口数量。

公开实验版本明确列出已支持命令；“首个稳定版”需覆盖 [architecture.md](architecture.md) 所定义的完整边界。性能调优贯穿阶段，但不得替代正确性门槛。

## 阶段 1：类型、协议与连通

已交付：`types`、`protocol`、`server`、Rust SDK 和 CLI；共享黄金/错误向量及真实 TCP / CLI 测试已建立。帧与 Value 的版本 1 编码已冻结。服务端支持 HELLO / PING / AUTH / SELECT / QUIT，串行执行连接屏障，拒绝未知命令。SDK 串行请求、校验 ID，发送后超时/断线暴露结果未知且不重放。Batch、EVENT / ACK 仅有编码，不提供执行或投递。实际构建与验证入口见 [README](../README.md)。

建立最小 Rust workspace、共享 Value、基础错误、协议编码器、TCP服务、Rust客户端和CLI。先实现 HELLO、PING、认证/选库屏障和明确的未知命令错误。

完成条件：10种Value的独立黄金向量、错误输入、半包粘包、版本拒绝、请求ID匹配通过；CLI能向真正的网络服务发请求。冻结首版网络编码候选，保存共享测试数据。

阶段 1 交付时尚无数据引擎；不能将该阶段的连通性视为完整缓存能力。后续开放范围以各阶段说明为准。

## 阶段 2：数据引擎与完整命令

已交付：单分片 `engine`、隔离数据库、通用数据命令、数值 / String / Bytes 和全部 List / Map / Set 命令，包含单分片多 Key 原子写入与集合 STORE。所有命名空间共享明确的引擎执行权；候选结果先检查，再整体发布。条目包含 generation、revision 和预留期限，实际变化才更新版本；提供全实例受管内存、每库 Key 配额与 noeviction 语义。

CLI / Rust SDK 已打通十种 Value 的真实网络往返；契约覆盖 Null / 缺失、数值边界、容器深度、失败回滚、容量与响应限额、数据库隔离、多连接自增和 MSET 原子可见性。源码、测试和公开 API 已补中英双语注释，公开文档缺失会导致构建失败。

阶段 2 交付边界：RENAME / RENAMENX / COPY / MOVE、KEYS / SCAN / RANDOMKEY、清库 / 交换随后在阶段 3 完成；TTL 设置和调度留到阶段 4，INFO / CONFIG / SHUTDOWN 留到阶段 6。Batch、事件、TLS 和客户端池尚未实现。完整已开放清单见 [commands.md](commands.md)。

先建立明确所有权的单Shard引擎，再补数据库隔离、通用命令、全部类型与容器操作。将TTL可见性字段和generation/revision纳入条目，避免后期改写数据模型。

完成条件：命令返回/错误/缺失/Null行为一致；数值边界、容器深度、内存及响应上限通过；没有隐式创建或部分字段写入。显式标注尚未实现的管理和跨Shard命令。

## 阶段 3：固定分片与资源预算

已交付：独立分片锁与有序协调、跨库复制 / 移动和重命名、全库交换 / 清空、连接绑定的 SCAN、字节匹配和随机查询、全实例内存及每库 Key 预算、五种淘汰策略。有界阻塞执行保持连接屏障；异步清库只延迟物理释放，退休索引在释放前仍计费。淘汰开启且配置限额时，该阶段写入保守锁定全实例；公开 TTL 设置随后在阶段 4 开放，ttl-first 无候选时拒绝写入。

契约覆盖跨分片独立推进、相反参数顺序无死锁、多 Key / SWAPDB 原子观察、迁入新身份及期限保留、游标弱一致性与会话隔离、失败不部分淘汰及异步回收预算。真实 TCP 与 CLI 已接入新增命令。GET / SET / 混合负载的引擎与网络基础测量各重复三次，原始数据和环境见 [testing.md](testing.md#阶段-3-基础测量)。

实现同Key顺序、跨Shard调度和固定顺序协调；完成多Key原子性、跨库命令、SCAN及数据库管理命令。建立全实例内存预算、noeviction及其他淘汰策略。

完成条件：并发观察看不到原子命令的中间状态；无死锁或无界队列；失败写入不遗留部分淘汰；清库/交换保持生命周期语义。记录基础吞吐、延迟和RSS，不预设必须采用某种分配器。

## 阶段 4：TTL完整生命周期

已交付：可注入的配对单调 / 墙钟、SET 四种到期选项、EXPIRE 系列、PERSIST 与四种查询。每次命令取得全部执行权后统一观察时间；所有读写入口严格过滤到期值。全实例有序索引每条目最多一个定时项，状态变更同步更新，后台按预算重验完整身份与双期限后释放内存；与请求共享有界执行许可。

契约覆盖边界、校时、溢出、版本耗尽、续期与删除重建、跨库迁移、清库、旧任务字段校验及条件写入 / 删除 / 复制 / 扫描竞争；真实 TCP / CLI 与空闲后台回收已验证。阶段 4 交付时事件禁用，重启缓存与 TTL 均为空，不提供可靠定时通知。

完成单调时钟期限、绝对时间换算、读路径到期过滤、后台回收与任务版本校验。先用可验证调度结构，再依据数据决定是否采用时间轮。

完成条件：续期、PERSIST、删除重建、过期与条件写入竞争全部通过；后台调度暂停仍无过期读取；高频续期内存有界。此时可以发布明确标注能力的内存缓存预览版。

## 阶段 5：事件、Journal与故障恢复

已交付：六类事件、复合身份、Fast 有界队列及丢弃计数；Reliable v1 统一 Journal 事务、逐事务 fsync、目录独占、拓扑 / CRC 校验、尾部截断、检查点原子替换和保留。普通变更在同步后发布；TTL 到期先不可见，记账失败保留条目并阻止受影响分片写入；不确定同步后禁止继续追加和持久 ACK。

已接入配置、专用 TCP 订阅、命名组 / 临时会话、ACK 空洞、窗口、租约重投及 Offset 超期。Rust SDK / CLI 提供显式消费，完整连接池和多语言客户端留到阶段 6。真实 TCP、CLI、强制终止服务进程及同步故障注入验证已提交记录恢复与缓存冷启动为空；未做长期压力、吞吐或物理断电验证。

先固定事件类型、身份与Fast有界投递，再实现Reliable统一Journal事务、组与ACK、重投、保留和容量背压。必须在落盘前冻结磁盘格式和版本策略。

完成条件：跨Shard事件原子提交、fsync故障、截断与恢复、ACK空洞、组隔离、ID连续和offset超期测试通过；重启缓存为空的边界明确。不能在故障测试完成前宣传可靠事件已可用。

## 阶段 6：客户端契约与运维

已交付：Rust、Go、Java 原生客户端的固定库连接池与独占租约、超时与取消、普通 Batch、专用事件订阅及显式 ACK。共享协议字节和命令向量通过真实 TCP 与双向 TLS 服务端验证；Go 使用标准库并执行 race 检查，Java 使用 JDK 17 的 javac / JSSE，无 JNI / cgo。三种 SDK 单连接串行，不自动重连或重放请求；发送后失败暴露结果未知。

服务端和 CLI 已支持 TLS / 双向 TLS、INFO、CONFIG GET / SET / RELOAD、Prometheus、text / JSON 日志与 SHUTDOWN。重载完整校验静态配置，仅允许日志级别变化；查询脱敏。运维、Batch 响应预算、证书 / 名称拒绝、池关闭、取消与未知结果均有契约测试。长期压力、资源耗尽及新增功能的性能成本留在阶段 7，不把此阶段视为生产验收。

完善Rust SDK/CLI的连接池、超时、订阅与取消，再实现Java和Go原生客户端。完成TLS、配置、INFO、Prometheus、日志与优雅关闭。

完成条件：三种SDK复用协议/命令测试数据并通过真实服务端测试；写入结果未知可辨识；关闭释放资源；配置重载与脱敏正确。不得以自动重试掩盖提交不确定性。

## 阶段 7：优化与首个稳定版

已交付：18 类负载各三次的引擎 / TCP / TLS 矩阵、Fast / Reliable 各 600 秒持续运行、每种模式 30 轮 TTL 观察，以及完整配置、源码 / 二进制摘要、直方图和 CPU / RSS / Journal 资源记录。资源契约覆盖五种淘汰策略、失败不提前淘汰、半帧与慢读端连接回收、超大声明帧拒绝、Journal 满时状态保留和 ACK 预留；另有固定种子的 20,000 次协议突变烟测。

根据实际负载定位 Reliable 消费重复扫描日志的成本，增加仅运行时的记录游标，并修复控制区压缩后候选游标失效；持续运行进一步定位无到期前缀时仍全量重写的尾延迟退化，已改为按资格维护并复测。原子事务、逐事务 fsync、ACK 和保留语义不变，新增同事务后继、过滤、追加、压缩与重启回归。数据与测量边界见 [testing.md](testing.md#阶段-7-本机验收)。

本机验收已完成，当前版本为 0.1.2 预发布版本，不将阶段编号完成等同于稳定发布。尚未执行 Redis 8 等价比较、目标生产环境多日压力或物理断电验证；发布评估必须补充对应证据。Fast 高负载消费者发生明确的 Offset 过期，Reliable 消费仍有积压；不宣称两倍 Redis、无限留存或消费者必然跟上。

按 [testing.md](testing.md) 执行可复现基准、热点与大Value负载、长时间运行和资源耗尽实验，测量Fast与Reliable的成本。只有定位瓶颈后才进行索引紧凑化、Slab/Arena、读路径或时间轮优化。

完成条件：公开首版契约有证据、重要正确性问题清零、资源边界可观测、文档与实际能力一致。附真实环境和性能结果；未达到两倍Redis目标时如实记录，不通过改变语义达标。

## 1.0.0 发布准备

目标是在后续几个月内发布首个稳定版，具体发布日期取决于下列验收结果；当前不将版本号改为 1.0.0。阶段 1—7 的本机交付是基础，不替代稳定发布门槛。按依赖推进，每一项保留可复现证据；本表的验收条件不表示已经全部执行。

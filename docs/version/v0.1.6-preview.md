## 主题与目标

内置更新（0.1.3 起）让「下载并替换二进制」成为产品行为，这条链路的可信度必须与它的权限相称。本计划针对既有验证链与验收缺口：仅核对同一 GitHub Release 的 `SHA256SUMS`，资产与校验和同源（S-02）；流水线输入需要固定和摘要校验（S-03）；安装包未签名；原生安装与升级的目标系统验收矩阵不完整（M-06）。本版已完成与未执行的部分见下文及 testing.md。

1. 发行资产可被独立验证：来源证明或签名，加 SBOM（S-02）。
2. 更新器按新的验证链检查，失败不修改已安装程序（S-02）。
3. 流水线输入固定：动作按提交摘要固定、工具链固定、MSRV 有 CI（E-05、E-06）。
4. 三平台原生安装、升级、卸载有可复核的证据（M-06）。
5. 更新器带来的依赖面有记录、有决策（S-06）。

## 不做的事

- 不改协议、Journal、命令与配置键；不改资产命名与目录布局。
- 不在 DEC-03 之前采购或假定证书；未签名状态继续如实写在 README 与 install.md。
- 不引入 winget、Homebrew、apt 仓库等分发渠道；列为后续评估。

## 工作包 4：原生安装验收（P0，状态：五平台托管 runner 通过，完整矩阵未完成）

0.1.6 已在五个托管 runner 实际通过安装、服务生命周期、同版重装、0.1.5 包升级及卸载保留；Unix 的真实 Reliable Journal 摘要未变，完整系统版本和证据见 testing.md。Windows Server 2022 不代替 Windows 11，Ubuntu 上 RPM 兼容演练不代替 RPM 系原生系统。公开候选上的真实 `ling update` 仍需发布后执行，脚本明确记为未执行（M-06）。

| 平台 | 包 | 环境要求 |
|---|---|---|
| Windows 11 x64 | Setup EXE、ZIP | 一次性虚拟机，管理员权限 |
| Ubuntu LTS x64 与 ARM64 | DEB | 带 systemd 的虚拟机或托管 runner |
| RPM 系发行版（任选一种） | RPM | 带 systemd 的虚拟机；容器不能验证服务 |
| macOS Intel 与 Apple Silicon | PKG | 各一台一次性主机或托管 runner |
| 缺少 FUSE 的 Linux 环境 | AppImage | 使用 `--appimage-extract-and-run` |

每项执行：首次安装；服务注册、启动、停止、重启；`ling-cli -c 'PING'`；同版本重装；从上一版本升级，包升级与 `ling update` 各一次；卸载。检查配置未被覆盖、卸载后服务已注销、配置与 Journal 保留。

| 任务 | 做法 | 验收 |
|---|---|---|
| 4.1 脚本化 | 把上述步骤写成只做断言与采集的脚本，不修改仓库，在一次性环境运行；托管 runner 能做的部分放进 CI，其余在虚拟机上手工执行 | 脚本与矩阵一同入库 |
| 4.2 记录 | 每项记录系统版本、包文件名与摘要、命令与结果；未执行的明确写「未执行」，不留空 | 结果写入 testing.md 新小节；install.md 中的已知限制同步更新 |
| 4.3 系统服务和原生安装器（E-10、E-11） | Linux 用打包配置验证放行目录下的 Reliable，并区分示例路径错误与服务权限。Windows 分别检查未启动安装器的取消、已启动后失败、助手状态停滞 | 记录非零原因、安装器是否真正启动和双程序版本；能证明无变更的不报「未知」，不能确认的不提示直接重试；不得关闭系统服务沙箱绕过路径问题 |
| 4.4 便携升级与中断（E-12、E-13） | 在隔离目录从 N 升到 N+1，核对程序及随版许可/声明；保留固定成员白名单。Unix 分步替换时在各边界中止进程再检查恢复，不动真实安装 | 正常升级两个版本号和声明均对应 N+1，配置未改；中断后可恢复至同一完整版本，或明确列出人工恢复步骤、备份位置并停止报成功。不以该演练替代物理断电验收 |

## 发布门槛与风险

P0：工作包 1 与 4。发布前：更新器验证链有正向与篡改的反向测试；原生安装记录写明系统版本与未执行项；纯文案改动检查链接与一致性。2026-11-17 所有者授权按当前验收范围发布 Preview，Windows 11、原生 RPM 系统、交互 UAC 取消继续顺延；不得将预发布视为完整目标环境验收。

- DEC-02 已选择 GitHub 构建来源证明；分支产物不具有正式版本的标签身份，仍需标签构建后独立验证。
- Windows 代码签名与 macOS 公证需要付费证书或开发者账户，且 SmartScreen 信誉要时间积累；DEC-03 未决前，未签名状态继续如实写在 README 与 install.md。
- 签名密钥丢失或泄漏的处置流程必须在启用签名之前写好：吊销方式、换钥发布、旧版本更新器如何信任新钥。
- 固定流水线输入会增加维护成本，由 Dependabot 的 PR 与定期人工复核承担；不以放宽固定来换取省事。

## 本轮实现与验收边界

来源证明使用共享多 subject 的 `PROVENANCE.sigstore.json`，覆盖 14 个包、14 份 `.cdx.json`、审计报告及校验清单，共 31 个发布附件。SBOM 明确是目标平台 normal/build 依赖清单，不伪造传递依赖为直接依赖图；Setup 包额外登记实际携带的 WinSW，ZIP 不登记未携带组件。`--check` 报告证明是否提供，安装才真正验签；官方 GitHub CLI 2.97.0+ 是明确的外部运行要求，信任根与轮换边界见 [DEC-02](../decisions.md)。

默认／无更新器测试、真实跨主机令牌隔离、验证失败不改安装文件、Unix 四文件中断恢复及 Windows helper 状态契约已执行。五平台构建、原生脚本、三平台真实离线验签、依赖审计与体积／双构建测量结果已记录于 [testing.md](../testing.md)。干净标签演练、Windows 11、原生 RPM 系系统、交互 UAC 取消及公开候选上的 `ling update` 尚未执行，不能将本轮开发构建称为完成发布验收。

# v0.3.0 预览版：目标环境验收

> 状态：最终验收计划草案，工具短测已完成，600 秒校准、30 轮 WSL 崩溃恢复与正式长测尚未开始。正式基线必须是已发布并核验来源的 0.2.0 二进制；条目编号引自 [baseline-0.1.3.md](baseline-0.1.3.md)，索引见 [README.md](README.md)。所有者于 2026-11-18 指定专用 WSL 及强制终止测试，并确定发布前 Fast、Reliable 各 72 小时。`ling-acceptance` 已可用，目标物理环境仍未确定。详见 [DEC-09](../decisions.md#dec-09本轮验收环境安排2026-11-18)。

## 主题与目标

roadmap.md 与 testing.md 已写明稳定版的门槛：目标环境的多日压力、物理断电和语义可比的 Redis 8 测量。当前这些证据不存在（M-03、M-04）。0.3.0 不新增产品功能，先准备并运行可用环境的验收。WSL 强制终止只能产生虚拟机/进程崩溃恢复证据，不能标为真实物理断电。发布后立即开展大量测试，发现的问题仅保存复现、影响和原始记录，后续统一修复。

1. 固定验收环境、计划和通过标准，并在执行前提交（M-01）。
2. 多日压力，覆盖 Fast 与 Reliable、各淘汰策略和连接抖动（M-03）。
3. 本轮先运行 WSL 崩溃恢复与可用的存储故障验收，物理断电保留为稳定版门槛（M-03）。
4. 与 Redis 8 做语义可比的测量（M-04）。
5. 持续模糊与并发检查评估（M-05、M-08）。
6. 补完运维手册（D-07）。

## 不做的事

- 不新增命令、配置键或存储格式。发布前发现阻断问题须评审并形成处理结论；发布后的扩大测试只记录问题，留待后续统一修复。
- 性能改动必须按 v0.1.5 的方法：先基线、单项变更、后复测。
- 不为通过标准而弱化 TTL、关闭 fsync 或丢弃事件（testing.md）。不写「零丢失」「生产可用」；可靠性描述必须带上提交与保留边界（AGENTS.md）。
- 结论只适用于被测的硬件、文件系统与设备写缓存设置，不外推到其他环境。

### 执行顺序与证据预算

1. 完成 0.2.0 发布，取得真实发布二进制并核验摘要和来源；记录准确发布提交、版本输出及二进制 SHA-256。冻结工具提交与脚本摘要。
2. 在没有其他验收服务运行时，先完成工作包 3 的 30 轮 WSL 崩溃恢复和相关存储故障验证。结束后确认无残留服务；强制终止不会与校准或长测并行。
3. 以工作包 2 的四实例 CPU 布局同时校准 600 秒。每种压力策略均需校准，`--seconds 600` 对 pressure 表示每策略 600 秒；shadow 独立校准 600 秒。校准数据不能算作正式运行时长。
4. 依据校准填写有效周期、观察间隔与消费覆盖门槛的具体数值；如需调整速率、慢消费参数或预算，重新校准受影响场景，将最终参数和门槛提交到 `main`。这些未决项未填满前不得启动正式计时。
5. 正式并行启动四实例，按下述连续性要求运行。长测期间不构建、不执行其他基准、不终止 WSL，不自动重放不明结果。
6. 核对全部适用门槛及证据后才评审 0.3.0 发布；发布完成后立即扩大测试并使用 `--stage post-release`，发现仅记录并留待后续统一修复。

每份输出保存 `environment.json`、冻结工具与二进制、每阶段配置、`progress.json`、`result.json`、`summary.json`、`resources.jsonl.gz`、完整 `errors.jsonl.gz` 和 `server-complete.log.gz`；可读服务日志尾部合计最多 8 MiB，不能把尾部轮转当作完整错误记录。发现样例上限 200，全部异常仍保存在压缩记录中；资源样本上限 100,000，5 秒间隔下覆盖 72 小时所需的约 51,840 次采样，正式运行不得触发样本省略。容量 SET 拒绝按 seed / worker / cycle 和参数摘要完整复现。每次采样前检查 ext4 与 WSL 宿主 `/mnt/c` 的实际可用空间，任一低于 10 GiB 就停止并保存证据，该轮不能判通过。

每个 Reliable 新实例的 Journal 限额为 4 GiB；pressure 每策略新建目录并保留旧目录，因此配置上界不能只按两个活动 Reliable 进程估算，五段加 shadow 最多涉及 24 GiB Journal 配额，另需日志、结果与 10 GiB 空闲余量。实际空间、保留压缩峰值和磁盘增长均从原始采样分析，不将配置上界当成实际写入量或持久性保证。

## 工作包 2：多日压力（P0，状态：未开始）

时长已经 DEC-09 确定：发布前 Fast、Reliable 各 72 小时。正式共四套独立服务和驱动并行：每模式 shadow 为单进程连续 259,200 秒，pressure 的五策略各 51,840 秒，合计有效负载时间 259,200 秒。pressure 按 `noeviction → lru → lfu → random → ttl-first` 顺序，每段新建服务和目录，段间仅允许启动及采集证据所需的间隔，该间隔不计入有效时长，不声称是单进程连续运行。shadow 意外重启或中断不能拼接成一次连续 72 小时；保留失败证据，评审后用新目录重跑。

### 四实例布局与固定参数

下表 CPU 均是专用 WSL 可见编号。每个服务和对应驱动各占一对 sibling，彼此不共享同一物理核；正式开始前再次保存 `lscpu` 拓扑与实际亲和性。四个实例分别使用独立端口、目录和二进制副本，shadow 与 pressure 不共享服务状态。

| 实例 | 服务端 CPU | 驱动 CPU | 正式时长 | seed | 受管预算 |
|---|---|---|---|---|---|
| Fast shadow | `0,1` | `2,3` | 连续 `259200` 秒 | `3002026` | 固定 noeviction、16 MiB、4096 keys |
| Fast pressure | `4,5` | `6,7` | 五策略各 `51840` 秒 | `3002027` | 每段 1 MiB、16 keys、32 KiB Value |
| Reliable shadow | `8,9` | `10,11` | 连续 `259200` 秒 | `3002028` | 固定 noeviction、16 MiB、4096 keys |
| Reliable pressure | `12,13` | `14,15` | 五策略各 `51840` 秒 | `3002029` | 每段 1 MiB、16 keys、32 KiB Value |

四实例均先以 2 workers、每 worker 每秒 5 个闭环周期校准；这是有界闭环速率，不是开放到达率，也不是实测吞吐承诺。正式参数只能在校准后、计时前修订并提交，不能运行途中为过门槛而修改。共用设置为：2 个数据库、4 个 shard；事件 buffer 4 MiB、retention 1 day；Reliable 每实例 Journal 4 GiB，保持逐事务 fsync；资源采样 5 秒、预热 3,600 秒；worker 每 100 周期主动重连。每库在生产前建立独立 fast / slow 命名组，共 4 组；slow 每条 ACK 前等待 0.05 秒，每 120 秒计划断开 0.2 秒再重连，fast 不设置计划掉线。slow 计划离线时间单独记账，不伪装为持续在线。

### 校准后必须补齐的数字

| 门槛 | 当前草案 | 正式计时前要求 |
|---|---|---|
| 每实例有效周期下限 | 待 600 秒校准 | 对 shadow 总周期和每种 pressure 策略分别填入 72 小时或单段的具体最小周期数，并写明按校准结果换算的保守系数；只存活不算有效压力 |
| 每观察区间的进展与间隔 | 待 600 秒校准 | 填入计数检查窗口、窗口内最小有效周期以及采样最大允许间隔；从完整 `progress` / 资源数据核对，不能以最终总数掩盖长时间停滞 |
| 消费覆盖与进展 | 待 600 秒校准 | 分四组填入 active / planned offline 的时长门槛、ACK 进展窗口及最小有效收发量；核对每阶段实际存活时间和退出原因 |
| 容量校准 | 3 秒短测已触限，正式布局仍待 600 秒校准 | 每种策略保存实际容量拒绝或 EVICTED 计数；不得以设置了小预算代替触限证据 |

3 秒容量工具烟测的 Fast / Reliable noeviction 各返回 53 次预期 `ERR_OUT_OF_MEMORY`，ttl-first 分别 49 / 46 次；LRU、LFU、random、ttl-first 均观察到 EVICTED。因此本轮 pressure 采用上表的 32 KiB / 1 MiB / 16 keys。默认 4 KiB / 2 MiB 在先前 10 秒烟测未触限，结合每分钟清库不能保证长期低负载实际触限，不作为本轮容量参数。

### 正式运行命令草案

在专用 WSL 中使用 Bash。先把 `LING_ACCEPTANCE_BINARY` 设置为已核验的真实 0.2.0 发布二进制绝对路径，把 `LING_ACCEPTANCE_REVISION` 设置为该二进制的准确发布提交，把 `LING_ACCEPTANCE_RUN` 设置为全新 ext4 输出根目录。它们必须来自发行核验记录，不能复用工具烟测候选路径或从当前工具 HEAD 猜测。以下命令已对应当前 `v030.py --help`，在校准门槛补齐并提交前只作为草案。

```bash
: "${LING_ACCEPTANCE_BINARY:?set the verified v0.2.0 binary path}"
: "${LING_ACCEPTANCE_REVISION:?set its exact release commit}"
: "${LING_ACCEPTANCE_RUN:?set a fresh ext4 output root}"
test -f "$LING_ACCEPTANCE_BINARY" || exit 1
test ! -e "$LING_ACCEPTANCE_RUN" || exit 1
mkdir -p "$LING_ACCEPTANCE_RUN" || exit 1
cd /root/ling-acceptance/source || exit 1
common=(--server-binary "$LING_ACCEPTANCE_BINARY"
  --binary-revision "$LING_ACCEPTANCE_REVISION" --stage pre-release
  --workers 2 --cycles-per-second 5 --churn-cycles 100
  --journal-bytes 4294967296 --sample-seconds 5 --warmup-seconds 3600
  --slow-consumer-delay 0.05 --consumer-reconnect-seconds 120
  --consumer-disconnect-seconds 0.2 --resource-samples 100000
  --finding-examples 200 --min-free-bytes 10737418240)

python3 -B benchmarks/v030.py "$LING_ACCEPTANCE_RUN/fast-shadow" "${common[@]}" \
  --event-mode fast --phase shadow --seconds 259200 --seed 3002026 \
  --server-cpus 0,1 --client-cpus 2,3 \
  > "$LING_ACCEPTANCE_RUN/fast-shadow-driver.log" 2>&1 &
fast_shadow_pid=$!
python3 -B benchmarks/v030.py "$LING_ACCEPTANCE_RUN/fast-pressure" "${common[@]}" \
  --event-mode fast --phase pressure --policy all --seconds 51840 --seed 3002027 \
  --payload-bytes 32768 --memory-bytes 1048576 --max-keys 16 \
  --server-cpus 4,5 --client-cpus 6,7 \
  > "$LING_ACCEPTANCE_RUN/fast-pressure-driver.log" 2>&1 &
fast_pressure_pid=$!
python3 -B benchmarks/v030.py "$LING_ACCEPTANCE_RUN/reliable-shadow" "${common[@]}" \
  --event-mode reliable --phase shadow --seconds 259200 --seed 3002028 \
  --server-cpus 8,9 --client-cpus 10,11 \
  > "$LING_ACCEPTANCE_RUN/reliable-shadow-driver.log" 2>&1 &
reliable_shadow_pid=$!
python3 -B benchmarks/v030.py "$LING_ACCEPTANCE_RUN/reliable-pressure" "${common[@]}" \
  --event-mode reliable --phase pressure --policy all --seconds 51840 --seed 3002029 \
  --payload-bytes 32768 --memory-bytes 1048576 --max-keys 16 \
  --server-cpus 12,13 --client-cpus 14,15 \
  > "$LING_ACCEPTANCE_RUN/reliable-pressure-driver.log" 2>&1 &
reliable_pressure_pid=$!
acceptance_status=0
for acceptance_pid in "$fast_shadow_pid" "$fast_pressure_pid" "$reliable_shadow_pid" "$reliable_pressure_pid"; do
  if wait "$acceptance_pid"; then
    acceptance_exit=0
  else
    acceptance_exit=$?
    acceptance_status=1
  fi
  printf '%s\t%s\n' "$acceptance_pid" "$acceptance_exit" >> "$LING_ACCEPTANCE_RUN/driver-exit-status.tsv"
done
exit "$acceptance_status"
```

校准使用相同布局与参数，把每条命令的 `--seconds` 改为 `600`、使用全新的校准输出根；pressure 因五种策略分别计时，总计 3,000 秒。正式预热仍固定为 3,600 秒，600 秒校准只验证执行能力、容量及工作量，不据此判断稳态资源斜率。正式命令应由可持续运行的会话保存驱动退出码，终端断开或宿主休眠不得被当成成功完成。

| 2.5 分析与消费验收（M-09） | 每段预热后最小二乘计算资源斜率，核对 Journal、生产周期、四组交付/ACK/ID/全时覆盖；按下面全部门槛判定 | 退出码、`criteria` 与分析共同判断；不能用进程存活、生产成功率或收到的事件均 ACK 代替全程有效工作量 |
| 2.6 处理发现 | 发布前按发布门槛处理；发布后的大量测试只记录失败输入、种子、环境、日志、复现步骤及影响，保留失败测试，不修改产品代码，留待后续统一修复 | 发现和证据一一对应；不得把未修复项写成已通过 |

### 正式通过标准

- 每个 shadow 完成连续 259,200 秒；pressure 五段各完成 51,840 秒。2 workers 均全程工作并正常停止，`workers_failed=0`，达到校准后提交的总周期和分窗口进展下限；四组消费覆盖完整阶段，只有事先计划的 slow 离线可扣除。所有适用 `criteria` 为真还不够，须逐项满足本文门槛。
- 全部资源样本的 RSS、累计 CPU、句柄和线程字段均有效，INFO 与 Prometheus 可获取且可解析，资源原始样本没有省略；采样覆盖起止和全时段，间隔符合校准后提交的上限。每段剔除前 3,600 秒后以样本实际单调时间做最小二乘，RSS 斜率不大于 `1 MiB/小时`，句柄与线程斜率各不大于 `0.1/小时`。各段独立判断，保留全部原始点和保留压缩时段，不用阶段平均掩盖失败段。
- panic、未预期错误、类型或内容不一致、TTL 错误、worker 异常退出、消费者非计划中断均为零。预期的错误类型/溢出/越界、TTL missing 等契约拒绝单列，pressure 的预期 `ERR_OUT_OF_MEMORY` 与合法淘汰 missing 允许；shadow 不能被容量拒绝降级。pressure 每种策略必须实际触限：noeviction 有 OOM，LRU / LFU / random 有 EVICTED，ttl-first 有 EVICTED 或因无可用 TTL 受害者而 OOM，并记录真实次数。
- 72 小时容量验收中 `ERR_JOURNAL_FULL` 不作为可接受的长期只读状态；发生 JournalFull、Journal I/O 故障或提交未知即记录并判该轮未通过，不能以服务仍存活或读请求成功放行。专用资源耗尽契约另行验收。
- 按生产、交付、ACK 与消费者存活分别核对。EVENT 的 stream_id / db / shard / sequence 合法，ACK 水位和乱序空洞可解释；收到的事件均确认也不代表所有生产事件都已交付。最终 pending、重复及离线窗口原样记录。工具可单列的 Fast slow `ERR_OFFSET_EXPIRED` 若导致组提前结束，仍不满足本轮快慢消费者全时覆盖，不能由工具的预期滞后分类直接放行；Reliable 不允许借此跳过历史或重建组。其余消费错误均为失败。
- CPU 亲和性、配置、工具、二进制与环境身份完整，磁盘余量 guard 未触发，所有 gzip 可完整解压；服务正常退出，任何中断和失败保留部分证据并记录，不拼接为成功。没有达到周期、资源或消费门槛的阶段，即使退出码为零也不得标为通过。

## 工作包 3：WSL 崩溃恢复与存储故障（P0，状态：未开始）

| 任务 | 做法 | 验收 |
|---|---|---|
| 3.1 WSL 强制终止循环 | 固定 seed `3002030`，持续写入中随机终止专用发行版；每轮保存实际延迟、成功响应、稳定事件标识及 ACK。重启核对保留期内已确认提交的事件、完整事务、stream_id、每个 db / shard 流序号，以及已确认 ACK 和待重投空洞；未知请求可出现或不出现 | 30 轮分别有完整记录；未知结果不重放；不能把 Batch 当事务，也不能要求恢复缓存值或 TTL |

| 3.3 存储故障 | 使用已有 Journal 资源耗尽、只读、尾部截断、中段损坏和 I/O 注入契约，按实际运行逐项列结果；需要设备映射的 dm-flakey / dm-log-writes 仍为后续物理专用机方案，不假称本轮已运行 | 与已有契约逐项对照，列实际新增覆盖、失败与未执行项；资源故障不与 72 小时服务共享目录或进程 |

Windows PowerShell 执行草案如下；`LING_ACCEPTANCE_BINARY` 是该发行版内的已核验发布二进制路径，`LING_CRASH_OUTPUT` 是不存在的宿主输出目录。实际随机时间范围及其他参数随冻结脚本的环境记录保存，30 轮不得替换为短烟测。

```powershell
python -B benchmarks/wsl_crash.py --execute --distro ling-acceptance `
  --binary $env:LING_ACCEPTANCE_BINARY --source /root/ling-acceptance/source `
  --output $env:LING_CRASH_OUTPUT --cycles 30 --seed 3002030
```

稳定版仍需目标物理机与独立负载机：通过可编程电源随机断电、在另一台机器保留成功响应与事件记录，并确认文件系统挂载、设备易失写缓存及必要的存储故障覆盖。macOS 的 `sync_all` 设备同步行为须对照实际 Rust / OS 版本核实后再纳入；这些物理组合、dm 故障重放与设备缓存边界均未因本轮安排而完成。

## 风险与未决

- WSL、CPU 布局与时长已确定，工具短测已完成；正式长测前仍需真实 0.2.0 发布二进制、30 轮独立 WSL 崩溃恢复、600 秒校准、具体工作量门槛和最终计划提交。
- WSL 强制终止只作用专用 `ling-acceptance`，必须先于长测且确认无其他验收任务。物理断电仍只能在后续专用物理环境执行。
- 多日运行失败后重跑成本很高。保留部分证据但不累计拼接 shadow 的连续 72 小时；pressure 仅允许上述五策略段间必要的进程切换间隔。
- 4 个实例共享宿主与磁盘，CPU 绑定不能消除宿主调度、热降频、休眠或 I/O 干扰。四实例校准必须记录实际吞吐并填写有效进展门槛，不能仅以存活时长判通过。
- Journal、日志和旧策略目录都占实际磁盘；达到磁盘余量保护或 JournalFull 会中止本轮通过判断。保留数据后再评审，不以缩短保留窗口、关闭 fsync 或清除失败证据换取通过。
- 发现的问题可能需要改变 Journal 格式。这属于格式版本变更，退出本版另行设计升级与回退，不静默修改 v1。
- Redis 对比容易被配置差异左右。配置全部公开；不满足可比条件的场景不报数字。
- 结论只适用于被测的硬件、文件系统与设备写缓存设置，不外推到其他环境。

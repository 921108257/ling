# v0.3.0 预览版：目标环境验收

> 状态：验收准备。基线为 0.2.0 发布后的 `main`；条目编号引自 [baseline-0.1.3.md](baseline-0.1.3.md)，索引见 [README.md](README.md)。所有者于 2026-11-18 指定先使用 WSL 及强制终止测试；专用发行版尚待可用，目标物理环境仍未确定。详见 [DEC-09](../decisions.md#dec-09本轮验收环境安排2026-11-18)。

## 主题与目标

roadmap.md 与 testing.md 已写明稳定版的门槛：目标环境的多日压力、物理断电和语义可比的 Redis 8 测量。当前这些证据不存在（M-03、M-04）。0.3.0 不新增产品功能，先准备并运行可用环境的验收。WSL 强制终止只能产生虚拟机/进程崩溃恢复证据，不能标为真实物理断电。发布后立即开展大量测试，发现的问题仅保存复现、影响和原始记录，后续统一修复。

1. 固定验收环境、计划和通过标准，并在执行前提交（M-01）。
2. 多日压力，覆盖 Fast 与 Reliable、各淘汰策略和连接抖动（M-03）。
3. 物理断电与存储故障，验证已确认提交的边界（M-03）。
4. 与 Redis 8 做语义可比的测量（M-04）。
5. 持续模糊与并发检查评估（M-05、M-08）。
6. 补完运维手册（D-07）。

## 不做的事

- 不新增命令、配置键或存储格式；发现缺陷后的修复只限正确性。
- 性能改动必须按 v0.1.5 的方法：先基线、单项变更、后复测。
- 不为通过标准而弱化 TTL、关闭 fsync 或丢弃事件（testing.md）。不写「零丢失」「生产可用」；可靠性描述必须带上提交与保留边界（AGENTS.md）。
- 结论只适用于被测的硬件、文件系统与设备写缓存设置，不外推到其他环境。

## 分级与门槛

P0：工作包 1 至 3。P1：4 至 6。发布门槛：P0 的原始数据与分析入库；每个发现都有处理结论（修复并回归、接受并写入限制、或推迟并说明）；未执行项在发行说明中逐项列出。

2026-11-18 所有者调整：本轮 Preview 的工作包 1 至 3 改在专用 WSL 中验收，工作包 3 使用测试发行版强制终止和存储故障测试。原文的物理机/远程电源条件保留为后续稳定版目标，不再阻塞本轮 Preview；报告必须区分 WSL 崩溃恢复与物理断电。WSL 尚未可用时只推进工具和计划，不把未运行项目标为通过。

## 工作包 2：多日压力（P0，状态：未开始）

时长由 DEC-09 决定。本文建议每种模式不少于 72 小时，这只是建议，不是已评估的结论。

| 任务 | 做法 | 验收 |
|---|---|---|
| 2.1 负载 | 混合读写，覆盖 String、Bytes、List、Map、Set；短 TTL 与长 TTL 并存，高频续期；大值与热点；多数据库；每种淘汰策略分段运行并触及上限；Fast 与 Reliable 各一轮 | 负载定义与种子写入计划 |
| 2.2 开放负载段 | 增加按固定到达率发送的开放负载段，观察过载下的排队与 ERR_BUSY；闭环负载不模拟无界到达（testing.md） | 记录过载下的错误分布与恢复时间 |
| 2.3 扰动 | 周期性断开与重连客户端；周期性 `CONFIG RELOAD`（仅日志级别）；周期性 `FLUSHDB`；指标抓取；消费者快、慢与反复掉线；Reliable 轮次中含强制终止后重启，检查 stream_id 与序号延续 | 每类扰动的次数与结果入库 |
| 2.4 影子校验 | 在独立的 Key 分区上，客户端维护参考状态并逐次比对值与类型；失败命令后确认状态未变 | 不一致数为零；任何一次不一致都附复现信息 |
| 2.5 分析与消费验收（M-09） | 记录稳态后 RSS 斜率、句柄、线程、Journal 字节、事件序号；沿用 0.1.5 工作包 1.5 按场景判定生产、交付、ACK 与消费者存活 | 对照运行时长与退出原因；预设的 Fast 滞后有单独记录，未预期的消费中断令该轮失败。保留原始数据，不用生产请求成功率代替消费验收 |
| 2.6 处理发现 | 发布前按发布门槛处理；发布后的大量测试只记录失败输入、种子、环境、日志、复现步骤及影响，保留失败测试，不修改产品代码，留待后续统一修复 | 发现和证据一一对应；不得把未修复项写成已通过 |

## 工作包 3：物理断电与存储故障（P0，状态：未开始）

| 任务 | 做法 | 验收 |
|---|---|---|
| 3.1 断电循环 | 物理机上通过可编程电源开关在随机时刻断电。写入负载持续，客户端把已收到成功响应的请求与事件标识记录到另一台机器。重启后启动服务端，核对：凡收到成功响应的提交，其事件都在恢复结果中；不存在不完整事务；各逻辑流序号连续；命名组 ACK 状态与已确认的 ACK 一致；无法确认的请求允许出现或不出现。服务端要么正常恢复，要么以明确错误拒绝启动，不要求人工修复 | 循环次数在 1.2 先定；每次循环的原始记录入库 |
| 3.2 文件系统与设备 | 至少覆盖 Linux 的一种常见文件系统，并记录挂载选项与设备写缓存状态；macOS 上先核实标准库 `sync_all` 的实际行为（据了解使用 F_FULLFSYNC，需对照所用版本源码确认），再决定是否纳入。每个组合单独报告 | 结果表按组合列出，不合并 |
| 3.3 非断电故障 | 评估 Linux 的 device-mapper 故障注入（如 dm-flakey）与写入日志重放（dm-log-writes）：在每个写入边界重放并检查恢复，需要 root，只在专用机器执行；另覆盖磁盘满与 I/O 错误 | 与现有 Journal 故障测试对照，列出新增覆盖 |
| 3.4 结论 | 报告写明：被测组合、通过的循环数、失败与异常、未覆盖的组合。不得写「零丢失」，只写在被测边界内已提交事件均被恢复 | 结论进入 testing.md 与 persistence.md 的限制说明 |

## 工作包 4：Redis 8 可比测量（P1，状态：未开始）

本机只有 Redis 7.0.15（testing.md），不能代替。目标是给出有边界的比较，不是排名。

| 任务 | 做法 | 验收 |
|---|---|---|
| 4.1 版本与配置 | 安装确切的 Redis 8 版本并记录；完整保存 Redis 配置，包括 io-threads、持久化、maxmemory 与淘汰策略 | 版本与配置随原始数据入库 |
| 4.2 可比范围 | 只比较语义可比的 String 与 Bytes 的 GET、SET，及带毫秒 TTL 的 SET；相同数据量、连接数、流水线深度、请求大小与命中率。ling 的 Fast 对照关闭持久化的 Redis；Reliable 对照 AOF 且每次写入同步的配置，但 ling 持久化的是事件而不是缓存值，两者持久化对象不同，报告里并列说明，不合成单一排名 | 可比范围与不可比项在报告开头列出 |
| 4.3 公平性 | 同机同硬件、同一压测客户端，两个系统交错运行，各至少三次独立重复；压测客户端不得占满全部 CPU 却不记录；报告 P50、P95、P99、P99.9、CPU、RSS 与受管内存 | 原始输出与环境入库 |
| 4.4 结论 | 「吞吐达到 Redis 8 的两倍」仍是研究目标，不是断言；未达到如实记录，不通过改变语义达标。自定义类型、命令差异与事件成本单列 | 结论写入 testing.md，附原始数据链接 |

## 风险与未决

- DEC-09 未决时工作包 1 阻塞，2 至 4 只能做脚本与计划方面的准备，不产生可引用的结论。
- 断电测试具有破坏性，只能在专用机器与可重装的环境上执行，不在开发者的日常机器上进行。
- 多日运行失败后重跑成本很高。按分段设计并保存中间状态；段间是否允许间断，要在计划里写明连续性要求。
- 发现的问题可能需要改变 Journal 格式。这属于格式版本变更，退出本版另行设计升级与回退，不静默修改 v1。
- Redis 对比容易被配置差异左右。配置全部公开；不满足可比条件的场景不报数字。
- 结论只适用于被测的硬件、文件系统与设备写缓存设置，不外推到其他环境。

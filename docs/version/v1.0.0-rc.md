# v1.0.0-rc：稳定候选

> 状态：规划，未开始实现。基线为 0.3.0 发布后的 `main`；条目编号引自 [baseline-0.1.3.md](baseline-0.1.3.md)，索引见 [README.md](README.md)。本文不承诺发布日期，是否进入稳定候选取决于下列进入条件，而不是时间。

## 主题与目标

稳定候选不是新特性版本。它做三件事：冻结公开契约，处置兼容名称，让发行流程能够产出正式版。进入后只接受阻断发布的修复；任何新增能力或契约变化都退回 0.x 线。

版本号使用 SemVer 预发布形式：Cargo 版本 `1.0.0-rc.1`，标签 `v1.0.0-rc.1`（发行流水线要求标签等于 `v` 加 Cargo 版本）。文件名中的 `rc` 是系列名。更新器按语义版本比较，`ling update --stable` 只选择正式版；rc 序列在预发布与稳定两个通道里的选择行为需要实测确认（工作包 3）。

## 进入条件

全部满足才能打 `1.0.0-rc.1`：

1. v0.1.4 至 v0.3.0 的 P0 全部完成，P1 要么完成，要么有书面顺延理由。
2. DEC-01、02、03、07、08、09 已有记录；DEC-04 至 06 只在选择独立发布仓内 SDK 时适用，「不发布」不阻塞 rc；DEC-10、11 按需。
3. 重要正确性问题清零：没有未处理的 L1；每个 L2 有「已修复并回归」「已接受并写入限制」或「已推迟并说明」的结论。
4. [roadmap.md](../roadmap.md) 1.0.0 发布准备的六项各有证据入口：1、2 已交付；3 见 v0.1.6；4 见 v0.2.0 与 v0.3.0；5 见 v0.1.5 与 v0.2.0；6 即本文。
5. 文档与实际能力一致：全文检索确认不残留过期的版本号与能力表述。

## 工作包 1：公开契约冻结（P0，状态：未开始）

冻结的意思是：之后的变更必须走显式的版本变更流程，不静默重新分配标签、改变语义或删除名称。

| 对象 | 冻结内容 | 验证入口 | 变更规则 |
|---|---|---|---|
| 网络协议 v1 | 帧头、帧类型、Flags、Value 标签与单位、错误帧、请求 ID 规则 | `tests/fixtures/protocol` 的黄金向量与错误向量 | 不兼容变更提升协议版本 |
| Journal v1 | 文件头魔数 `LGJRNL01`、记录与提交尾标、事件与消费组编码、检查点 | 独立磁盘向量与恢复契约 | 新版本须有升级与回退方案，不跨版本自动降级 |
| 错误码 | `ERR_*` 稳定字符串及含义 | commands.md 注册表与共享错误向量 | 只增不改；废弃要公告 |
| 命令集 | 命令名、参数类型、返回值、原子性、Batch 白名单 | commands.md 与共享命令用例 | 新增走次版本；改变语义视为破坏性 |
| 配置 | 十二组配置键、默认值、范围与重启要求 | config.md 与配置契约测试 | 弃用先告警至少一个次版本再移除 |
| CLI | 选项名、退出码语义、本地帮助的七种语言入口 | CLI 契约与帮助测试 | 同配置 |
| 客户端互操作 | 第三方实现可依赖的线协议、命令和错误语义；不冻结第三方语言 API | v0.1.7 工作包 4、5，独立向量与真实服务端 | 按协议版本管理。自愿独立发布的 SDK 另定 API 及支持周期 |
| 观测名称 | INFO 字段、Prometheus 指标名与类型 | 运维手册的指标参考 | 同命令集 |
| 打包身份 | 可执行文件名、服务名、安装路径、LaunchDaemon `io.ling.cache` | 各平台 verify 脚本 | 变更须提供迁移步骤 |

| 任务 | 做法 | 验收 |
|---|---|---|
| 1.1 清单核对 | 逐行对照上表与当时的 main，列出未冻结或与文档不一致的项，每项给出处理 | 差异清单为空，或每项有结论 |
| 1.2 向量齐备 | 确认协议、Journal、错误码、命令各有独立于被测编码器的期望字节或期望结果，不只靠「编码后再解码」 | 缺口补齐后再冻结 |
| 1.3 独立实现核对 | 从接入文档查找握手、十种类型、错误/结果未知、确认与共享向量；不要求下载任何官方 SDK | 能用固定字节和预期结果验证协议；未维护的绑定和未发布的包均不是稳定版门槛 |

## 工作包 2：兼容名称处置（P0，状态：阻塞于 DEC-08）

更名时保留的兼容名称，若带进 1.0，就等于变成长期契约；之后要移除就是破坏性变更。因此每一项的去留必须在进入 rc 之前决定，决定权在所有者，实现者不代选。

| 名称 | 位置 | 现状（文档） | 可选处置 |
|---|---|---|---|
| `linger.toml` | 前台运行时的配置回退 | 当前目录没有 `ling.toml` 时读取 | 保留为文档化别名；或读取时告警并写明移除版本 |
| `LINGER_PASSWORD` | CLI 密码环境变量 | `LING_PASSWORD` 缺失时回退 | 同上；告警文本不得回显凭据 |
| Prometheus `linger_*` 指标 | `/metrics` | 沿用旧前缀 | 重命名须在至少一个次版本内同时输出新旧两套名称，否则会破坏已有仪表盘与告警规则；双份输出的开销按 v0.1.5 的方法测量 |
| Java 包 `io.linger.cache` | Java SDK | 保留兼容身份 | 保留；或迁移包名并在一个次版本内提供旧包的转发类 |
| Go 模块路径 | 仓内 Go 客户端 | `linger.local/cache` | 未独立发布则保留并说明本地使用限制；只有选择迁移时才需落实 DEC-04 |
| `LINGER_TEST_ADDR` | Go、Java 契约驱动 | 仅测试使用 | 不属于公开契约，可改名，须同步驱动脚本 |
| `linger-server`、`linger-cli`、`Linger Cache DB` | 旧可执行文件与安装目录 | 不自动迁移（install.md） | 保持不迁移，在 1.0 迁移说明中保留一节 |

| 任务 | 做法 | 验收 |
|---|---|---|
| 2.1 决策记录 | 对上表每项写明「保留为受支持的别名」或「弃用」；弃用须写明起始版本、告警方式与移除版本 | DEC-08 的记录入库，覆盖全部行 |
| 2.2 落实 | 弃用项增加告警，并同步 config.md、cli.md、install.md 与七种语言帮助；保留项把「兼容」改写为「受支持的别名」。涉及配置键或环境变量的行为变化，先修订规范再改代码 | `cargo test -p ling-cli-help` 与 CLI、配置契约通过；全文检索无冲突表述 |
| 2.3 测试 | 别名优先级（`LING_PASSWORD` 先于 `LINGER_PASSWORD`，既有契约已覆盖的不重复）；弃用告警不含凭据；指标并存期两套名称取值一致 | 新增用例通过 |

## 工作包 3：发行通道与更新器（P0，状态：未开始）

现状（代码）：`release.yml` 对每个 `v*` 标签用 `--prerelease` 与固定的 Preview 标题创建 Release，并断言资产数恰为 14；`site/build.mjs` 在页眉、页脚与首页多处硬编码「pre」与「预发布」字样（E-07）。按现有流程发布不出稳定版，`ling update --stable` 也在此基线上没有可选版本（E-09）。

| 任务 | 做法 | 验收 |
|---|---|---|
| 3.1 通道判定 | 从 Cargo 版本推导：版本含预发布标识（连字符），或主版本为 0，创建预发布 Release；否则创建正式 Release，标题不再固定带 Preview。判定不手写在标签名里 | 对 `0.3.0`、`1.0.0-rc.1`、`1.0.0` 的表驱动脚本测试 |

## 撤回与回滚

本节是预案，更新器与发布任务的实际行为在实施前须对照源码核实（本次审查没有通读 `update.rs`）。

- 发现严重问题时，不移动或重写已推送的标签，不替换已发布资产。做法是发布修复版本，并把问题版本的 Release 标注为已知问题；是否将其改为草稿或删除，取决于更新器读取 Release 列表的方式，先实测再定，避免用户被更新到问题版本。
- 更新器不允许降级（install.md），因此回退到旧版本只能手动安装旧包。回退说明写入发行说明：缓存值与 TTL 本来就不恢复；Reliable 的 Journal 在协议 v1 与 Journal v1 未变的前提下可被旧版本读取，拓扑不一致时旧版本会拒绝启动，不会静默改写。
- 若某个 rc 引入了格式或协议变更，视为违反冻结规则：该 rc 作废，不得提升为 1.0.0，须按版本变更流程提供升级与回退方案后重新进入 rc 序列。
- 发布后发现的问题按 1.0.x 处理，只收修复；新增能力走 1.1，破坏性变更走 2.0，不在 1.0.x 内引入。

## 风险与未决

- DEC-08 与 DEC-12 未决时，rc.1 不能发布：前者决定冻结内容，后者决定观察期与批准人。
- 前序版本顺延的 P1 项会在这里集中暴露。进入条件 1 要求每项有书面顺延理由，rc 阶段不再接收「先发布后补」的承诺。
- 签名与公证（DEC-02、DEC-03）若仍未采购，1.0.0 将以未签名状态发布。这是允许的，前提是 README、install.md 与发行说明都如实写明，并保留可独立验证的来源证明。
- 证据范围只覆盖被测的硬件、文件系统与设备写缓存设置，1.0.0 的声明必须带着这些边界，不外推到未测环境。
- 1.0.0 之后，冻结清单中的名称、标签与格式就是长期契约。拿不准的条目，宁可留在 0.x 或标注为实验性，也不要带进 1.0。
- 稳定版的承诺强度取决于 v0.3.0 的实际结果。若断电或多日压力发现未修复的数据一致性问题，不进入 rc，不以说明文字代替修复。

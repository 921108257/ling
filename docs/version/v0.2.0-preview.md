# v0.2.0 预览版：Reliable 与连接模型

> 状态：发布准备，尚未发布。Linux 首轮约 52% 的积压确认吞吐回退已由 `508d39c` 修复，干净构建三次复测消除；Windows 三次 30 秒补测确认的尾延迟回退已列为 Preview 限制，保留关闭通知的选项。完整证据见 [testing.md](../testing.md#020-首轮通知对照2026-11-18)。基线为 0.1.7 发布后的 `main`（`89076a4`）；条目编号引自 [baseline-0.1.3.md](baseline-0.1.3.md)，索引见 [README.md](README.md)。设计契约 `7116411` 已先于实现合入 main；测量工具见 `8ecb2aa`，连接准入实现见 `ba119bb`。评审决定见 [decisions.md](../decisions.md#020-执行模型评审2026-11-18)。

## 主题与目标

0.1.x 不改变执行模型。0.2.0 是第一个允许改变执行模型的版本，所以升到 0.2.0：Reliable 写入的提交方式、连接内的请求并发、订阅的投递驱动均列入最初候选范围。每一项都以前序版本的测量为前提，没有数据支持的项目记录「不实施」并关闭，不为凑齐范围而实现。以下保留原候选目标与任务，当前范围以各工作包状态及验收清单为准。

1. 设计先行：先修订 architecture、persistence、protocol、events、config，评审通过后再实现（工作包 1）。
2. Reliable 组提交，降低逐事务 fsync 的成本（P-05、R-05）；本轮决定不实施。
3. 连接内流水线，使 pipeline_enabled 与 max_inflight_per_connection 真正生效（F-01、D-04、R-05）；本轮顺延。
4. Windows Reliable：实现，或写入正式的不支持矩阵（F-03）；本轮选择继续不支持。
5. 订阅由提交唤醒（P-02）；明文 TCP 增加有界拒绝帧，TLS 握手期限继续复用现有配置（R-03、R-04）。本轮实现已完成，待完整验收。
6. 评估项：淘汰写入并发、命名组管理、证书热加载（P-06、F-02、F-04）；前者与热加载不实施，命名组管理顺延。

## 兼容性声明

- 协议 v1 的帧头、Value 标签、错误码注册表与 Journal v1 磁盘格式不变。Reliable 保持逐事务 fsync，每个事务仍是带完整提交尾标的独立记录。若实施中发现必须改动其中任何一项，该条目退出本版，改走协议或格式的版本变更流程。
- 本轮不实施组提交或连接流水线，三个预留配置保持已公开的串行/逐事务语义。实施项为可关闭的订阅通知与明文 TCP 有界连接拒绝；TLS 超限仍在握手前关闭。`events.notification_enabled=false` 保留 0.1.7 的 10 ms 派发路径。

## 不做的事

- 不改变「先 fsync 后发布」，不暴露未同步状态，不放宽任何原子性或屏障语义。
- 不引入缓存持久化、死信、每组保留、集群或复制；这些仍属 architecture.md 已排除或后续评估的范围。
- SDK 不自动重放写入；v0.1.7 的恢复策略语义延续。

## 工作包 1：设计评审（P0，状态：已完成并合入 main）

| 条目 | 需要修订的规范 | 必须回答的问题 |
|---|---|---|
| 1.1 组提交 | persistence.md 的提交顺序、architecture.md 的并发与原子性、config.md 的 group_commit_ms | 当前事务在持有执行权期间完成 fsync，状态在 fsync 之前不得发布，同一分片上的后继事务必须等待，所以组提交只能合并分片集合互不相交的事务；预期收益取决于这类并发的占比，由 v0.1.5 工作包 7.1 的数据决定是否实施。fsync 失败影响整个组，须与「统一物理 Journal 进入全局故障状态」的既有规则一致。group_commit_ms 的语义（有积压才等待，还是固定等待）与默认值：默认 2 ms 若是固定等待，会抬高轻负载下每次 Reliable 写入的延迟。结合 P-09、P-10 的锁范围与到期记账测量；优化不得漏记到期或逆序加锁 |
| 1.2 流水线 | protocol.md 的请求排序、architecture.md、config.md、sdk.md | 同一连接同一 Key 的顺序、屏障与多 Key 命令的关系。资源预算：现在请求等待者总量受连接数约束，允许每连接 1024 个在途请求后，上界变成 max_connections × max_inflight（默认值下约一千万），而单个请求可达 64 MiB，必须设计全局的在途字节预算与准入顺序，否则违反「所有队列有界」。排队超时仍只在执行前返回 ERR_BUSY；乱序响应下 Batch 的响应预算 |
| 1.3 订阅唤醒与读游标（P-11 至 P-13） | events.md、persistence.md、architecture.md | 据 0.1.5 测量选择追平时不复制整个 Fast 队列、Reliable 的记录内游标或有界索引。比较多事件事务、重投和重复 ACK；压缩/恢复使物理游标失效时仍按逻辑位置继续。验收区分已交付重复 ACK、被过滤从未交付、历史已被清理；不能只凭水位判成功，若 v1 在清理后缺证据先明确保留边界，不暗改磁盘 |
| 1.4 连接拒绝 | protocol.md、sdk.md | 超限时先写带 ERR_BUSY 的 ERROR 帧再关闭；写入须有极短期限，避免被慢客户端反过来拖住 |
| 1.5 Windows | persistence.md、architecture.md、install.md、README | 见工作包 4 |

验收：每个条目的规范修订经评审并合入 main，规范与现有行为的差异逐条列出；评审结论包含 go / no-go 与「不做的理由」。

|---|---|---|---|
| 2.1 立项条件 | P-05 | v0.1.5 工作包 7.1 的数据显示 fsync 占 Reliable 写入延迟的主要部分，且多连接下存在大量互不相交分片的并发事务；否则记录「不实施」并关闭本包 | 结论与原始数据一并写入 testing.md |
| 2.2 实现 | P-05、R-05 | 追加记录仍在事件提交锁内完成，其后在锁外等待一次覆盖多个事务的 fsync（领队与跟随者）；各事务持有分片执行权直到 fsync 返回，之后才发布并响应。事务仍是独立记录，Journal v1 不变。ACK 与检查点记录是否纳入组提交由 1.1 决定，保守起见本版只合并事件事务 | 磁盘向量与既有恢复用例全部通过，记录字节不变 |

| 2.5 配置与默认 | config.md | 让 group_commit_ms 生效并定义明确；默认值依 1.1 的结论，可能改为 0（不主动等待）；范围校验不变 | config 契约测试；默认值变化写入发行说明 |
| 2.6 复测 | P-05 | v0.1.5 的 Reliable 场景（无消费者、快消费者），并发连接数 1、4、16、32，改动前后各三次以上；报告吞吐、P99、P99.9 与 fsync 次数 | 轻负载下延迟不得变差，变差须在默认值上解决 |

## 工作包 3：连接内流水线（P1，状态：已推迟）

缺少规定的流水线深度与连接数对照，本轮保持单连接串行。下表保留后续候选任务，不作为已实现能力。

现状（代码）：读任务通过容量为 1 的通道向主循环交付帧，每条请求执行并应答之后才处理下一条（`crates/server/src/connection.rs:30-43,56-259`）。`pipeline_enabled` 与 `max_inflight_per_connection` 通过校验但不生效（R-05）。

| 任务 | 来源 | 做法 | 验收 |
|---|---|---|---|
| 3.1 准入与预算 | F-01 | 按 1.2 的设计实现：读任务在准入前检查每连接在途数与全局在途字节预算，达到上限就暂停读取，由 TCP 背压传导，不排无界队列。请求等待者总量的新上界写入 architecture.md | 资源契约：在途请求占满时，慢读端与半帧连接仍被回收（沿用 resources.rs 的方式），内存占用有上界 |
| 3.2 顺序与屏障 | F-01、D-04 | 同一连接上同一 Key 的操作按接收顺序执行；多 Key 命令是涉及分片的顺序屏障；AUTH、SELECT、QUIT 要等前序请求全部完成，其后请求使用变更后的状态（protocol.md 已有要求）。首个实现建议响应按请求顺序发出，把乱序响应留给后续评估；这只是建议，由 1.2 评审决定 | 同一连接流水线发送一串 INCR 再 GET，结果与串行执行逐项一致；屏障之后的请求观察到新库号 |
| 3.3 超时与关闭 | F-01 | 排队超时仍只在执行前返回 ERR_BUSY；已开始的命令不以超时宣称回滚；关闭期限取消连接，已开始的阻塞命令仍会完成（architecture.md）。流水线下，超时请求之后已在途的请求如何处理，由 1.2 决定 | 参照 `saturated_queue_rejects_before_engine_mutation` 新增流水线用例 |

| 3.5 SDK | F-01 | 服务端先行，用测试客户端验证。三种 SDK 的默认行为（单连接串行）不变；是否开放单连接并发接口，等服务端数据出来后另立条目，不在本版承诺 | 现有 SDK 契约全部通过 |
| 3.6 复测 | F-01 | 流水线深度 1、8、32，连接数 4 与 32，TCP GET、SET、混合三类，对照 0.1.7；报告吞吐、P99、P99.9 与 RSS | 原始数据入库；深度 1 不劣于 0.1.7，超出噪声须解释 |

## 工作包 4：Windows Reliable（P0 为决定，P1 为实现；状态：已完成决定，本轮不支持）

本轮选择 4.2 的出口 (b)，支持矩阵已同步，不实施 4.3。Windows 目录同步的最小 API 实验见 [persistence.md](../persistence.md)，不等于替换与断电持久性验收，也未证明必须放宽 unsafe 限制。

现状（文档）：Reliable 需要文件同步、目录同步与原子替换；Windows 路径尚未实现，配置校验返回 ERR_CONFIG_INVALID，不创建 Journal 目录，也不降级为 Fast。工作区设置了 `unsafe_code = forbid`。persistence.md 明确不允许用省略目录同步或静默降级来绕过限制。

| 任务 | 来源 | 做法 | 验收 |
|---|---|---|---|
| 4.1 能力核查 | F-03 | 在 Windows 上用实验与官方文档确认，不凭记忆：文件内容同步能否由标准库完成；重命名替换是否原子并覆盖已有目标；是否存在不用 unsafe 就能让目录项持久的办法。若只能通过平台 API 实现，就需要 unsafe 或第三方封装，触及 DEC-11 | 结论与实验方法写入 persistence.md 草案 |
| 4.2 决策 | F-03 | 只有两个出口：(a) 实现，并达到与 Linux 相同的 persistence.md 契约；(b) 不实现，写入正式支持矩阵。不允许引入弱化语义的第三种模式 | 决策记录引用 4.1 的实验结果 |
| 4.3 实现（仅 a） | F-03 | 目录独占（`fs2` 已是依赖，需核实其 Windows 行为）、追加、压缩与替换路径；故障注入与强制终止恢复契约在 Windows 运行（目前 Windows 的 CI 任务不运行这些测试），衔接 v0.1.4 的工作包 7.2。物理断电证据归入 v0.3.0，在此之前 Windows Reliable 不标为稳定 | Windows 上的 crash_recovery 与 Journal 故障用例通过；CI 纳入 |
| 4.4 文档 | F-03 | 无论 (a) 还是 (b)，同步 architecture、persistence、install、config 与 README 中的 Windows 表述；(b) 时在 install.md 增加支持矩阵，保留现有 ERR_CONFIG_INVALID 的明确提示 | 全文检索 Windows 与 Reliable，无冲突表述 |

## 风险与未决

- 订阅通知改变派发方式，默认启用；`events.notification_enabled=false` 保留 0.1.7 的派发路径，发布前验证关闭时的行为回归。连接拒绝是明确的协议可见变化，仍为尽力交付。
- 后续若重新立项组提交或流水线，它们会改变分片执行权的持有时间或请求的排队方式，可能让尾延迟变差。以 P99、P99.9 复测，变差不用平均吞吐的提升来抵消。
- 后续流水线的在途字节预算必须全局有界且可观测，避免在单连接上形成队头阻塞。
- Windows 本轮已选择 4.2 的出口 (b)，继续明确拒绝 Reliable；后续是否采用平台 API 或调整 unsafe 限制，需在持久性实验和独立设计后重新决定。
- 任何条目被证明需要改变协议帧、Journal 格式或错误码注册表时，该条退出本版，改走版本变更流程。
- DEC-09 已指定专用 WSL；0.3.0 发布前 Fast 与 Reliable 各连续运行 72 小时。WSL 崩溃恢复不等于物理断电，Windows Fast、WSL Reliable 与目标物理环境的证据分别记录。
